# Grimoire

Grimoire is the Witchy project and package CLI. Use `grimoire build`, `run`, `test` and `lock` for projects, `grimoire keygen` for a publisher key and `grimoire publish` to publish signed packages to Coven. [Install the tools and publish to a loopback server](docs/coven-http.md)

Use `grimoire web build` to build [Coven's Glamour catalog](../coven/witchy2/web/README.md) from reviewed dependencies.

`grimoire run` builds a local Witchy 2 executable and runs it with the Witchy Wasmtime host. With both tools on `PATH`, run the included example from this checkout.

```sh
./grimoire run examples/local-run/app
# 8080
```

The example reads a port from `settings.conf`. Its executable passes a single read-only file to a sibling Witchy package, which parses the decimal port. Change the number and rerun to see the new value. The executable uses 3000 for malformed contents. [Executable manifest](examples/local-run/app/witchy.toml) · [Package list](examples/local-run/app/main.packages) · [Config reader](examples/local-run/config-reader/reader.wy)

Grimoire reads project manifests, grant documents, lockfiles, and executable
policies from regular files, with a 32 MiB limit for each. Coven accepts up to 128 KiB for publication
manifests. The compiler applies its 64 KiB limit to native launch plans.

Registry review uses one captured policy for the staged program and its
dependency pins. A draft or acceptance compares the current file with
the reviewed bytes before replacing it and refuses to publish if that
comparison detects an intervening edit.

## Bootstrap

To install the tools into a prefix under your home directory, use `install.py` (docs/coven-http.md, "Install the pre-release tools"): it builds both binaries offline with MBX, places the engine's crypto library beside it, installs Grimoire and Coven with every module they load, and checks the result. To run from checkouts instead:

The launcher needs Python 3.11+ and matching `witchyc` and `witchy-wasmtime-host` binaries. To build them offline, use a Witchy 2 source checkout, Rust/Cargo, MBX, and the host's locked Cargo dependencies in the local cache.

```sh
witchy_src=/absolute/path/to/witchy/witchyc
export CARGO_TARGET_DIR=/absolute/path/to/build-output
mbx build --frozen --manifest-path "$witchy_src/Cargo.toml" --bin witchyc
mbx build --frozen --manifest-path "$witchy_src/tools/wasmtime-host/Cargo.toml" --bin witchy-wasmtime-host
export WITCHYC="$CARGO_TARGET_DIR/debug/witchyc"
export WITCHY_WASMTIME_HOST="$CARGO_TARGET_DIR/debug/witchy-wasmtime-host"
```

The example is proof-free. Programs requiring proofs also need the compiler's trusted Lean configuration. The example's `main.policy` names its package `@config-reader`, which needs Witchy 2 at `9c8ac74b` or later.

## Local projects

- Run `grimoire run` beside `witchy.toml`, or pass a directory or manifest path. The `[run].entry` and `[grants].document` paths start at the manifest directory.
- Use Witchy's native `main.packages` beside `main.wy`. Each line names a local source file, for example `config-reader 0.1: ../config-reader/reader.wy`. Witchy resolves `import "@config-reader"` against that list for the whole program. The version is a label. An adjacent `main.policy`, when present, applies during the ordinary compiler build. It names a package imported by name as `@name`, wherever its copy is.
- Use the executable's grant document to bind a `File<Read>` parameter by name, for example `config = "settings.conf"` under `[files]`. A single granted file (`[files]`, or an `[input]` file) is placed by the rule a granted directory is: on the document's word alone it is a file inside the project, with no component beginning with `.`, and not a manifest, lock, policy, package list, grant document or `.wy` source (a link is judged by where it leads). Any other file, such as `/etc/hosts` or a key under the home directory, needs the operator's word at each launch, for exactly that path: `grimoire run --allow-read-file /etc/hosts`, shown as `grant: file: /etc/hosts, read-only, OUTSIDE the project, named by the operator at this launch (--allow-read-file)`; `review` shows `OUTSIDE the project` and the flag a run needs. Grimoire's and Coven's state is never granted. Decision (2026-11-22, independent review): before, a document could name any file its operator can read, while a directory outside the project already needed `--allow-read-root`; a program's own sources are not granted because a file a build reads is not data. Witchy resolves file paths from the document's directory and rejects whitespace or glob characters in the resulting grant flag. Omitting the document supplies an empty set of named grants.
- This milestone supports console output, heap allocation, one input (`[input]`: a file or the launch's standard input, below), one read-only file per run, one loopback listener (`[listen]`, `127.0.0.1:PORT` or `[::1]:PORT`), one directory (`[dirs]`: read-only, or writable when the document says so, below), the clock (`[clock]`), fixed secrets and a `SecretStore` (below). No outbound network grant is given: a `[net]` section in the executable's document is refused before anything is read or built, whatever `main` takes (`test_any_net_grant_is_refused_whatever_main_takes`). [`examples/http-file-server`](examples/http-file-server/README.md) serves files from a signed package and lists each grant's syntax, engine flag and checks. Console output and heap authority require explicit `output = true` and `allocator = true` respectively under `[grants]`. Grimoire reads grants only from the executable's manifest and the document it selects. Wasmtime receives a private, freshly compiled module and checks its imports before executing it.
- `grimoire new NAME` writes an executable project (manifest, grant document, policy, a `main.wy` and a declared test) and `grimoire new NAME --lib` a library (manifest, source, a native `test.wy`). `grimoire new NAME --service` writes a service run once for each connection (`main(connection: Socket, data: Dir, allocator: Allocator)`, the listener granted as that connection, a `data` directory inside the project to read and write, `deadline-ms = "none"` and each connection's limits in `[run]`, and a native test of its answer as a function of the request's bytes). `grimoire new NAME --tool` writes a tool in a pipe (`main(args: Args, input: Console<Read>, console: Console<Write>, allocator: Allocator)`, granted `[args]` and standard input, with a `[[test]]` that gives both). The four are exclusive. Each builds and passes as written; nothing is granted that the program does not use, and an existing path is never replaced. `review --write-policy` drafts over the policy any of them wrote.

### A native executable (macOS or Linux ARM64)

A grant document with `[launch] version = 1` is a native launch plan (Witchy's
`docs/native-trusted-executables.md`): the compiler checks it and embeds it in a manifest-bound
executable, which refuses anything the plan does not declare. The document
selects native mode, and Grimoire selects the ARM64 target for the host.
On Linux, use a glibc system with `cc`, Landlock, and seccomp. See the
[native target requirements](../witchyc/docs/native-backend.md).

- `grimoire review` prints `witchyc native-plan` as `grant:` and `limit:` lines, and where each
  secret descriptor's bytes come from.
- `grimoire build` writes the executable to `target/ENTRY` through the resident compiler's
  `build-native` request (the inputs' key and the manifest's digest, checked again before it is
  published). With a compiler wrapper, Grimoire uses a one-shot
  `witchyc build` with the host target and the same manifest digest.
- `grimoire run [-- --NAME VALUE ...]` starts the executable directly, in the project's
  directory, with only the words given for declared path or object arguments, only the
  variables the plan's `[env]` grants, standard input only when the plan's `[input]` takes it,
  and no descriptor but one pipe per secret. Each secret is a declared `fd` argument with
  `secret = true`, its slot `from = { from = "arg", name = FLAG }`; the manifest says where
  Grimoire reads it: `[native] secrets = { FLAG = "env:NAME" | "fd:N" }`. An `fd:` source's
  slot also declares `object = { from = "arg", name = OBJECT }` (`type = "object"`), which
  Grimoire fills with that file's `DEVICE:INODE` so the runtime keeps every grant from it; the
  operator cannot set it. A secret's variable may not also be granted through `[env]`. The
  executable runs in a session of its own, and its whole group is stopped when it ends or the
  launcher stops. Output is made plain
  and a line that begins as Grimoire's or the runtime's is marked `| `, unless `--raw-output`.
- Refused: `[net]` and `[exec]` (Grimoire grants neither for any target), a descriptor argument
  that is not a secret's, a secret the executable would read itself (`env:`/`fd:` in the plan),
  and `--record` and `--bind`.
- Placement: a plan's directory and file roots given as a literal, cwd or home source follow
  the same rule as a Wasm run's: strictly inside the project, no hidden component, not a build
  file or tool state, or named exactly at this launch by `--allow-read-root`,
  `--allow-write-root` or `--allow-read-file` (shown `OUTSIDE the project`). A root's path has
  no `.`, `..` or empty component, a directory states its rights (parsed as a Wasm run's are),
  and each root carries `identity = { from = "arg", name = ID }` (`type = "object"`): Grimoire
  passes the `DEVICE:INODE` of what it examined, and the executable refuses any other object. A root the operator
  gives as a declared argument is the operator's choice and is shown as such; absent, its
  declared default is placed by the rule. `review` prints a `grant: placement:` line for each.

### A directory the program may write

```toml
# main.grants.toml: main(data: Dir)
[dirs]
data = { root = "data", rights = ["Read", "Write"] }
```

A run is shown `grant: directory: /abs/data, read and write (no symbolic link followed, no other device entered)` before it starts. `rights = ["Write"]` (`Dir<Write>`) is `write-only`. The right must be stated: a `Dir` or `Dir<Write>` parameter whose entry states no rights is refused with the line to write, and a right the document cannot state (`"Execute"`) is refused naming the entry. Every check of a directory still applies (real directories only, opened from `/` without following a link, on a local disk, nothing mounted below, not `/dev` or `/proc`, one directory a run, none while the program takes any secret).

**Where a granted directory may be** (decision of 2026-11-22, after an independent review found that a list of forbidden places let `.git`, `~/.ssh`, a sibling project and the temporary directory through: such a list cannot be finished). The rule says where a directory *may* be, and it is the same for reading and for writing, since what a program reads can leave through any channel it has:

- A grant document grants a directory **strictly inside the project directory** (the one holding `witchy.toml`), on its device, with no component below the project whose name begins with `.`. Not the project directory itself.
- Any other directory needs the operator's word **at each launch**: `grimoire run --allow-write-root /abs/path` (or `--allow-read-root`), exactly the document's root and its right. Never from the document alone, never from a dependency, never remembered. Its line says `OUTSIDE the project, named by the operator at this launch`; `review` and `build` show `OUTSIDE the project: a run is refused unless its command line names it`. A flag that matches nothing the document grants is refused.
- Either way, refused: a root that is or holds `/`, the home directory or the temporary directory (where Grimoire stages builds); any project kept *in* one of those; a hidden component (`~/.ssh`, `~/.config`).
- Either way, the tree is read at launch, without following a link, and refused if it holds version-control state (`.git`, `.hg`, `.svn`, `.jj`, `.bzr`) at any depth, or more than 100000 entries. A writable one is also refused if it holds an entry at its top level beginning with `.` (but the engine's own `.witchy-staging`, below), anything named `witchy.toml`, `witchy.lock`, `*.policy`, `*.packages`, `*.grants.toml` or `*.wy` in any case of its letters (`Main.WY`), any name with a character outside ASCII, or a hard link to a protected file.
- A second layer, by device and inode, for a writable root: it neither holds nor is the project's manifest, lock, entry, policy, package list, grant document, sources, a checkout package's source, the `[registry] path`, Grimoire itself, the Python that runs it, the compiler, the engine, Coven, the checker; and it is not inside Grimoire's or Coven's state, the module cache, the proof cache or the registry.

What Grimoire examined is what the engine is given, and it stays data during the run: the engine is told the directory's device and inode (`--dir-id`) and runs nothing if another directory is at that path by then, and under `--data-only` a program can name only **data names**. So a `.git` that appears after the scan is never traversed, and no source can be planted. What remains outside this: another local process changing the tree's ordinary files during the run, and a hard link to a protected file placed after the scan, which the program could read (never write through: files are replaced).

**Data names: one rule for the scan and the engine** (decision of 2026-11-22, after a security review: the engine's first rule listed what to refuse, and APFS resolved `witchy.loc` + KELVIN SIGN as `witchy.lock` and `main.grant` + LONG S + `.toml` as `main.grants.toml`; the scan compared with case and passed `Main.WY`). The rule is stated in Witchy's `docs/wasm-files.md` ("Data names") and is the same in both places:

- A **data name** is 1 to 255 bytes, each an ASCII letter, a digit, `-`, `_` or `.`, the first not `.`. A program in a granted directory can give no other name, for any operation, at any depth: no space, no letter outside ASCII, nothing hidden.
- A **protected name** is `witchy.toml`, `witchy.lock`, `*.wy`, `*.policy`, `*.packages` or `*.grants.toml`, compared without ASCII case. In a directory the run may write it is not a data name: the engine makes, replaces, renames (to or from), removes, reads and enters none, and the scan refuses a launch that finds one.
- `list` shows a program the entries it could name, and no others.
- The scan refuses a writable directory holding a name with a character outside ASCII: the engine never made it, and a file system may resolve it as a protected one. Other names a program cannot give (a space; a hidden entry below the top level) are left alone, unseen. A directory only read may hold any names; the program sees the data names among them.

**The engine's unfinished writes: `.witchy-staging`.** The engine writes a file whole under another name and renames it into place, so a reader sees the old contents or the new. A run killed between the two (`kill -9`, a power cut) leaves that temporary behind. It used to be a hidden sibling of the file (`.wal.log.witchy-PID-N`), which the scan above refused at the next launch and the program could not remove: a service killed mid-write stayed down until an operator deleted the file (4 of 20 kill rounds in the second dogfooding pass). Now the engine keeps every temporary in one directory of its own at the top of the granted directory, `.witchy-staging`, made (mode 0700) at the first write. No program can name it or see it in a listing. The scan accepts exactly it, checked to be a real directory, on the granted directory's device, the user's own with mode 0700 exactly. What it holds is the engine's to judge, under its lock, before `main` runs: only regular files with one name each, named `PID-N`, or nothing runs. (Grimoire used to look inside too, without the lock, and so refused a healthy directory beside a working engine: 866 of 86,000 scans in an independent review, 2026-11-22. For the same reason an entry that disappears while the tree is read is taken as gone, and the engine now makes a file that must not exist with one exclusive rename, so no file has two names for a moment.) Anything else under that name is refused, with a line that says not to remove it while a run is using the directory. The engine removes what a killed run left there before `main` runs, if no other engine is at work in the directory (each holds a lock on it while it runs). No operator action, and no check loosened. A temporary left beside the data by an engine older than this is still refused, once, with a line saying what it is.

The engine writes a file by replacing it (never through an existing hard link), follows no link, and enters no other device; it gives a program no operation that makes a link. Making or moving a name costs 256 of `file-bytes` whatever it holds, and a run makes at most `file-entries` names. A package gets the directory only if `main` hands it over, and only up to the `Dir<Read>`, `Dir<Write>` or `Dir` its policy line allows. A dependency's own manifest, grant document, `test.wy` and fixtures are never read, built or run by the consumer's `build`, `review`, `run` or `test` (`test_a_dependencys_tests_and_fixtures_are_never_read_built_or_run`); a registry release holds its source files (the entry and exactly the files of its own directory it imports) and nothing else.

### Input: a tool in a pipe

A program takes input only as a parameter of `main`, granted by its own document, like everything else: `main(console: Console<Write>, input: Console<Read>, allocator: Allocator)`.

```toml
# main.grants.toml
[input]
input = { stdin = true }     # this launch's standard input; or a file: input = "requests.txt"
```

`printf '1 + 2' | grimoire run` then gives the program those bytes. Each run shows `grant: input: this launch's standard input, read as the program asks for it` and `limit: input: N bytes in all; the read past them ends the run` (`[run] input-bytes`, default 65536, any number up to 2^40, or `"unlimited"`, shown as `limit: input: UNLIMITED: ...`). Standard input is a stream: the engine hands it over as the program reads, so a tool in a pipe answers before its input ends and reads more than its memory holds. A run whose input passes its limit ends there with an error, after it has run on, and written output from, what came before. An input file is read whole before the program starts (`limit: input: N bytes; a longer input is refused whole`, at most 16 MiB), and one longer than its limit is refused whole. Without the grant, standard input does not reach the engine at all. A run has one input, and no input (file or standard input) is granted while the program takes secrets. A file is examined without following a link, must be a regular file, and goes to the engine with its device and inode (`--input-id`): the engine opens the path without following a link and runs only if it opened that very file, so anything put at the path after the look is refused, not read. From a terminal the program waits for each line the operator types; the deadline still holds while it waits. A `[[test]]` may give `stdin = "text"`; without it a test's standard input is empty.

There are no command-line arguments yet. The agreed shape (docs/decisions.md in the compiler, 2026-11-22) is a `main(args: Args)` parameter granted by `[args] args = true`, shown as `grant: arguments: N words after --`; it needs a new capability type in the compiler and engine, so until then a tool's parameters arrive on its input or in a granted file.

### Output and limits

Standard output is passed on as the program writes it, a line at a time, and made plain: every control character but newline and tab (ESC and carriage return among them), every byte that is not UTF-8, and the characters that reorder or hide text are written out as `\x1b` or `\u{202e}`, so a program cannot move the cursor, recolor, or rewrite what the operator has read. Every line Grimoire writes of its own on standard error begins `grimoire: ` (a run's grants and limits are `grimoire: grant: ...` and `grimoire: limit: ...`), and every line of the engine's begins `witchy: `; each tool writes them through one function, so no message can lack its prefix. A line the program begins `grimoire:` or `witchy:` is marked `| ` in front, so nothing a program prints reads as said by either. What the compiler or Coven says while a run is built is passed on as theirs, without a prefix, before the program has written anything. A tool that needs the program's bytes as they are is run with `grimoire run --raw-output`: the operator's choice at that launch, which no manifest key can make. `grimoire test` compares the raw bytes.

**A quiet run.** `grimoire run --quiet` prints one line, `grimoire: grants as reviewed (digest HEX)`, in place of the `grant:` and `limit:` lines, when `grimoire review --accept` on this machine recorded exactly these. The record is a SHA-384 over the manifest's path and bytes, the grant document's bytes, the lock's bytes (each, or its absence), and the `grant:` and `limit:` lines exactly as the review showed them; `review --accept` keeps it under `$XDG_STATE_HOME/grimoire/reviewed/`, named by that digest, and a kept file is read only if it holds those very bytes. Any change to the three files, or to any line a run would show, is another record, and the run shows every line after one that says why it is not quiet (`grimoire: not quiet: ...`). The words after `--` are this launch's operator's own and are not part of the record (a review is given none). Warnings, refusals and the engine's lines, its last `witchy: limit: used:` line among them, are never left out. Decision (2026-11-24): the flag is the operator's, on the command line only, like `--raw-output`. The record is this machine's, never the project's: a record a project carried would let its author hide its grants from a quiet run. The one line saying why a run is not quiet is kept because the operator asked for quiet: the full lines alone would read as a flag ignored, and the change since the review is exactly what the operator should read.

Everything else Grimoire shows goes through one escaper too, whoever wrote it. For the length of a command its standard output and error, and those of every tool it starts (the compiler, Coven, the test host), are pipes read by Grimoire, which passes the text on under the same rule: a compiler diagnostic that quotes a package's source line, a file or package name, a registry's reply cannot act on the terminal. No call site chooses this, and `--raw-output` does not turn it off (it is about the running program's output only, which the engine writes to the real stream). Files (`--record`, a module, a lock) keep their exact bytes. A run that a limit ends has shown what it wrote, and the last line on standard error says which limit: `limit reached: deadline: the run was stopped after its 120000 ms (--deadline-ms)`. The first time a byte budget is used up the engine says so once (`limit reached: network bytes: ...`); the program is told too, and answers as it sees fit.

`[run]` sets the limits. They are never authority: each only ends a run, or one operation, sooner. Each that applies is passed to the engine as a number, the default included, and shown as a `limit:` line; a key for a grant the run does not have, an unknown key, or a value out of range is refused.

| `[run]` key | Default | Range | Shown as |
| --- | --- | --- | --- |
| `deadline-ms` | 1000 | 1 to 600000, or `"none"` | `limit: stops after N ms`, or `limit: no deadline: runs until it ends, is stopped, or its launcher ends` |
| `fuel` | 1000000 | 1 to 10^12, or `"unmetered"` | `limit: stops after N instructions`, or `limit: instructions are not counted` |
| `fuel-per-connection` (with `[listen]`) | none | 1 to 10^12 | `limit: stops after N instructions between accepted connections (...)` |
| `connection-deadline-ms` (with a `[listen]` grant `main` takes as a `Socket`) | 10000 | 1 to 600000 | `limit: each connection: stops after N ms (that connection is closed; the server goes on)` |
| `net-bytes` (with `[listen]`) | 1048576 | 0 to 2^40 | `limit: network: N bytes sent and received in the whole run` |
| `file-bytes` (with `[dirs]` or `[files]`) | 1048576 | 0 to 2^40 | `limit: files: N bytes read and written in the whole run` |
| `file-entries` (with a writable `[dirs]`) | 256 | 0 to 1000000 | `limit: files: N files and directories made in the whole run (...)` |
| `output-bytes` (with output) | 65536 | 0 to 2^40 | `limit: output: N bytes written in the whole run` |
| `input-bytes` (with an `[input]` grant) | 65536 | 0 to 2^40, or `"unlimited"`, for standard input; 0 to 16777216 for a file | `limit: input: N bytes in all; the read past them ends the run`, or for a file `limit: input: N bytes; a longer input is refused whole` |
| `net-bytes-per-connection`, `file-bytes-per-connection`, `file-entries-per-connection`, `output-bytes-per-connection` (for a program run once for each connection, with the grant each bounds) | none | as the run's key; `output-bytes-per-connection` at most 268435456 | `limit: each connection: N bytes sent and received (that instance sends and receives no more; the server goes on)`, and so on |
| `memory-pages` | 4 | 4 to 32768 | `limit: memory: N pages of 64 KiB, the program and its heap together` |
| `module-bytes` | 65536 | 8 to 16777216 | `limit: module: N bytes of code` (shown when set) |
| `heap-pages` (with the allocator) | 3 | 3 to 16384 | `limit: heap: B bytes, in N pages of 64 KiB of program memory (built into the module)` |
| `slots` (with the allocator) | 64 | a power of two, 64 to 1048576 | `limit: allocations: N alive at once (built into the module)` |
| `stack-bytes` | 16384 | a multiple of 8, 1024 to 65536 | `limit: stack: N bytes of call frames (built into the module)` |

The Wasm engine starts the `[run].deadline-ms` timer after Grimoire has
built the program. With the standalone Lean checker, each proof
invocation has a separate ten-second deadline. If `grimoire run` reports
that the standalone checker exceeded it, compilation stopped before
guest execution. A failed compilation leaves any previous run record
intact. The compiler's [phase measurements](../witchyc/docs/wasm-phase-measurements.md)
report SDK fingerprinting and Lean request time for successful builds.

Wasm executable builds check `module-bytes` before replacing the requested
output. If the compiled module exceeds the limit, an existing output
remains intact. Library builds produce source packages and use their
package limits.

Every Grimoire Wasm run gives the engine a lifeline, a pipe whose write end only the launcher holds. If the launcher exits or is killed, the engine detects the closed pipe and shuts down. Use `deadline-ms = "none"` for a service. The engine requires a lifeline for runs without a deadline. `fuel-per-connection` sets the instruction count back to N each time the program accepts a connection, and after each blocking accept that waited its whole two seconds with no one there. `fuel` is then the count for start-up. A request that loops runs out and ends the run with `limit reached: instructions: ...`.

**Arguments.** A program takes the words of its launch as `main(args: Args)` (`import args`: `args.count()`, `args.get(&allocator, index)`), granted by its own document: `[args] args = true` (at most 16 words and 4096 bytes) or `args = { count = 4, max-bytes = 256 }`. The operator gives them after `--`: `grimoire run . -- 1 + 2`. Everything after the first `--` is a word for the program and never an option of Grimoire or the engine. They are shown before the run, each in quotes and escaped: `grant: arguments: 3 given after `--`: "1" "+" "2"` and `limit: arguments: at most 4 words, 256 bytes in all; a launch with more is refused`. Words for a program whose `main` takes no `Args`, more than granted, a word that is not UTF-8 or holds a NUL: refused before anything is built. A dependency sees a word only if the program passes it one. A `[[test]]` gives them as `args = ["1", "+", "2"]`.

**A program for one connection.** When `main` takes a `Socket` (`main(connection: Socket, data: Dir, allocator: Allocator)`) and the document grants it as the listener is granted (`[listen] connection = "127.0.0.1:8080"`), the engine accepts and runs the program once for each connection, in a new instance: `grant: connections: accepts connections on 127.0.0.1:8080 (loopback only) and runs the program once for each, in a new instance that keeps nothing from the last; dials nothing`. The instruction count is then each connection's (`fuel-per-connection`, or `fuel` where that is not set; never `"unmetered"`), shown as `limit: each connection: stops after N instructions (...)`, and so is `connection-deadline-ms`. A connection that traps or reaches either ends alone, and says where it stopped as a run that traps does (`witchy: connection 7 stopped in `handle`: overflow +`). The byte budgets are the whole run's; each may also be given a connection's own (`net-bytes-per-connection`, `file-bytes-per-connection`, `file-entries-per-connection`, `output-bytes-per-connection`), which ends only that instance's use of it. Beside a connection's own, and only there, the whole run's may be `"unlimited"` (`net-bytes = "unlimited"`), shown as `limit: network: UNLIMITED for the whole run ([run] net-bytes = "unlimited"): only each connection's own net-bytes-per-connection bounds it`. Only the executable's own `witchy.toml` sets these: a package's manifest is never read for a run. One connection runs at a time; the engine accepts ahead and holds up to 1024 waiting, so a burst of clients past the system's own queue is answered, not reset. State that outlives a connection is kept in the granted directory. Such a program is granted no secret and no input.

**When a limit is reached** the engine says so once on standard error, naming the `[run]` key that sets it: `limit reached: file bytes: the run has read and written its 1048576 granted bytes ([run] file-bytes); ...`, and for instructions `the instruction budget ran out: raise [run] fuel-per-connection (the work after one accepted connection), or [run] fuel (the start, before the first)`. Grimoire tells the engine each limit's name (`--limit-name`); the engine's own flags are never what an operator is told to change. **Running out of `fuel-per-connection` ends the whole server, not that connection**, and the line says so. That is decided, not an omission: a program is one instance, and one stopped part-way through a request has memory no proof describes (a length written and its element not, an owner moved and not returned), so it is never run again. A service that must survive a costly request bounds its own work per request and answers 503, or gives the task a time limit (`answer_within`). What an engine-side per-connection limit would need (an instance per connection, or snapshot and restore; both measured at about 10 µs) is in Witchy's `docs/decisions.md` (2026-11-22).

**What a run used.** When a run ends, however it ends (it finished, a limit, its deadline, its launcher gone), the engine's last line is `witchy: limit: used: instructions 20183 of 1000000 at the start ([run] fuel), at most 13544 of 2000000 after one accepted connection ([run] fuel-per-connection); network 88801 of 1048576 bytes ([run] net-bytes); files 9950 of 1048576 bytes ([run] file-bytes), 3 of 256 made ([run] file-entries); output 0 of 65536 bytes ([run] output-bytes); memory 4 of 4 pages`: each count beside the key that bounds it. For a server the instruction figure is the most any one connection used, which is what `fuel-per-connection` has to cover. A run stopped from outside says the counts as of its last accepted connection, and says so. Ctrl-C and SIGTERM say it too (`witchy: stopped: interrupted (SIGINT); the run ends`, then the line); for a service each connection's own budget is shown beside the most one connection used of it, and for standard input how much was read. The allocator's own high-water mark inside the module's heap is not visible to the engine and is not in the line.

**A budget that is used up** is told to the program as `TooLarge`, from a file operation (`FsError`) and from a socket or `accept` (`NetError`): not `Io`, and for the rest of the run. A server that goes on answering after it can only answer errors; one that ends its loop on `TooLarge` ends the run, the line above says what ran out, and a supervisor can start it again.

**The module's own memory** (`heap-pages`, `slots`, `stack-bytes`; decision of 2026-11-22). The last three keys are not the engine's to enforce: the compiler builds them into the module (the allocator's layout and the stack's place), so they go to the compiler with the grant review, which keeps them for the build it reviewed (`prepare-grants ... PAGES SLOTS STACK`, Witchy `work/runtime-2` or later; an older compiler refuses a manifest that sets them, and builds the defaults as before). A module built with other sizes is another module: its bytes and its digest in a run's record differ. What they bound: the heap is everything in program memory above 98304 bytes (3 pages leave 98304 bytes: `read_text` of a 48 KiB file fails there); every `String`, `Vec`, map table and deque alive at once is one slot (64 means at most 63 `String`s beside the allocator's own use). A failed allocation is an `Err` in the program, never a trap. `memory-pages`, the engine's limit, defaults to what a module of these sizes has (its memory plus the allocator's own: 4 for the defaults, 10 for `heap-pages = 8`, `slots = 128`) and is refused if set lower. The cases of a native test (`test fn`) keep the default heap.

Package suites start at `test.wy`. Run `grimoire test .` to check and execute the native cases and then the executables declared with `[[test]]`. A case may take `&Allocator` (a fresh, bounded heap), so `Vec`, `String` and `HashMap` code is tested natively. [Package test authoring, grants and session protocol](docs/package-tests.md)

## SQLite

A Wasm project whose `main` takes `db: Sqlite` can grant an existing
database from its grant document.

```toml
[sqlite]
db = { file = "data/items.db", read = ["items"], insert = ["items"] }
```

Keep the database in a private directory inside the project. Paths are
relative to the grant document. Use `read`, `insert`, and `delete` to name
specific tables. Use a separate launch with `create` to provision tables.
Each launch grants one transaction. `reply_bytes` sets the reply bound,
including the status byte, up to 2 MiB.

`grimoire run` shows the database, operation and table grants before
launch. The Wasmtime host checks the database and its sidecars and enforces
the table rights. SQLite runs use the host's one-shot grant profile.

## Fixed secrets

A program that needs a key takes it as a parameter of `main` (`alpha: Secret<Seal>`, or `Secret<Reveal>` to read it), and the executable's own grant document approves it by name, its use and its sources (Witchy 2 `d476170d` or later; `--secret-object` needs `499f8240` or later; docs/wasm-capabilities.md, "Fixed secrets"):

```toml
[secrets]
alpha = { use = "seal", from = "env:ALPHA_KEY", also_from = ["fd:3"] }
```

```sh
ALPHA_KEY=... ./grimoire run app            # alpha from its `from`
./grimoire run app --bind alpha=fd:3 3<key  # or one of its `also_from`, named explicitly
```

- Grimoire reads the slots from the executable's grant document, and only from it: a dependency's manifest or document cannot supply a secret or another source for one. `wasm-grants` must then propose exactly those slots, with the same use and `from`, or nothing is built.
- Before anything is fetched or built, Grimoire selects each slot's source and reads it: `from`, or the source `--bind NAME=SOURCE` names, which must be the slot's `from` or one of its `also_from`. There is no fallback to another source. A duplicate, undeclared slot or undeclared source, an unset variable, a descriptor Grimoire was not started with, a value over 64 KiB, or a descriptor whose writer has not closed it within five seconds stops the run, naming the slot and the kind of failure, never the value. Prefer `fd:N` sources: a variable is in the environment of whatever started Grimoire.
- When it starts, Grimoire takes every variable outside the toolchain's list (`PATH`, `HOME`, `TMPDIR`, locale, `XDG_STATE_HOME`, `COVEN`, Lean's paths, and the `WITCHY_` variables the compiler and its proof helper read, each named, such as `WITCHYC` and `WITCHY_PROOF_CACHE`) out of its own process. Any other `WITCHY_` variable, such as `WITCHY_SECRET_X`, is taken out like the rest. It unsets them and overwrites them where the process was started with them, which is what `ps -E` and `/proc/PID/environ` show. So no fetch, check or build step is given one, or can read one from Grimoire. Each step is also started with only the toolchain's variables. The two layers each hide the other's removal in a real launch, so `tests/test_environment.py` checks each directly. A secret cannot be one of the toolchain's variables, nor any `WITCHY_` variable (reserved for the toolchain).
- One source, one route. Two `fd:` sources open on the same file or pipe (the same device and inode, whatever the numbers) are refused before the build, as is a `[files]` grant whose file is an `fd:` source's file, under its own name or a hard link, before the engine starts. That check is only a pre-check, to stop before the build: a granted name can become the key's file after it. So for each `fd:` source (a regular file, a named FIFO or a pipe: they cannot be told apart, and the flag only adds refusals), Grimoire also gives the engine `--secret-object=SLOT:DEV:INO`, that file's device and inode (never its path or value). The engine then refuses the file through every grant, under any name, when it is opened and when it would be written, removed or renamed. The flag can only add restrictions: the engine uses the list only to refuse, and a wrong identity could only refuse more. An `env:` source has no file to name, and a copy of a key file is a different file: keep key files outside what `[files]` names. While a program takes secrets, a `[files]` grant must be a regular file, which also refuses every spelling of a descriptor alias.
- The engine gets each value on a fresh pipe of its own, and those pipes are the only descriptors it gets besides the standard three. The slot's flag names the pipe (`--secret-slot=alpha:seal:fd:N`). The engine's environment is empty, its arguments never hold a value, and `--record` records the selected source, not the pipe.
- If Grimoire cannot take the launch environment out of its own process, it stops. On Linux, Grimoire and the engine also make themselves non-dumpable, so a process of the same user cannot read their memory. The launch-environment test checks Grimoire's dumpable setting on Linux.
- What remains: the process that started Grimoire keeps its own copy of a variable. On macOS, a same-user process with debugger rights can read the values in Grimoire's or the engine's memory.

## A store's secrets

A program that looks keys up by name takes a `SecretStore` (`main(store: SecretStore)`), and the grant document lists the names and what each may do (Witchy 2 `a3bbee89` or later, for `@fd:N`):

```toml
[secrets]
store = { SIGNING_KEY = "seal", REPO_TOKEN = "reveal" }   # "seal": sign only; "reveal": read and sign
```

```sh
SIGNING_KEY=... REPO_TOKEN=... ./grimoire run app
```

- Each name is the launch variable it is read from, as before (the engine's rule), but Grimoire reads it, before anything is fetched or built, and gives the engine the value on a fresh pipe of its own: `wasm-grants`' `--secret-seal=SIGNING_KEY` becomes `--secret-seal=SIGNING_KEY@fd:N`. The engine reads no variable, and its environment stays empty. An unset variable or a value over 64 KiB stops the run before the build (`secret SIGNING_KEY: missing input (env:SIGNING_KEY)`), naming the secret, never the value.
- The same rules as a fixed secret's `env:` source, all checked from the document before the build: not one of the toolchain's variables, nor any `WITCHY_` name; not a name a slot also lists as `env:` in `from` or `also_from` (one source, one route); not a name granted as ordinary environment through `[env]` (a slot's `env:` source neither). The `[files]` gate above applies whenever the program takes any secret, a store's included. A store secret has no file, so there is no `--secret-object` for it.
- `wasm-grants` must propose exactly the store's secrets Grimoire read, with the same use. A store table that no `SecretStore` parameter takes stops the run before the build: its values were read for nothing. A slot and a store secret may have the same name; each gets its own pipe.
- `--bind` selects a slot's source only; a store secret always comes from its variable.

`tests/secret_run.py` signs with two `Secret<Seal>` slots and checks each one's HMAC tag. It records every toolchain step's and the engine's environment, arguments and inherited descriptors, and the environment of the process that started each step, and checks that no canary appears in any of them. It also covers `--bind` to an `also_from` descriptor, refusals before the build (including two descriptors on one file), a `[files]` grant that is a secret's file or a hard link to it, the same hard link made after Grimoire's check (the build step makes it, and the engine refuses it through `--secret-object`), a selected regular-file source, the held identity of a pipe source, and a registry dependency that declares secrets. `StoreRun`, in the same file, does the same for a `SecretStore`: a sealed key and a token it reads, each giving its HMAC tag, with the same canary checks and the engine given only its pipes; a store beside a slot of the same name; and refusals before the build (an unset variable, a name that is also a slot's source or `[env]`, a toolchain or `WITCHY_` name), the `[files]` gate with only a store, and a store no parameter takes. Witchy 2's host fixtures (`secret-object-*`) check that the flag cannot widen anything, and `secret-store-fd*` check the `@fd:N` store flags. Signing needs the compiler's proofs, so these checks also need `WITCHY_WASM_READY_BINDING` (and, for speed, `WITCHY_PROOF_CACHE`). Without them they fail and say so.

The host suite checks graph resolution, owner and operator decisions against real lock and trust files. The remaining registry integration cases exercise staging, executable policy, signed format migration and toolchain pins. The signed localhost witness publishes, admits, restarts the server, then locks, builds and runs a fresh consumer.

```sh
python3 tests/run.py                       # default host suite
python3 tests/run.py --http-witness         # signed localhost restart and clean build
python3 tests/run.py --process-boundaries   # listener, signals, file replacement and secret delivery
python3 tests/test_native_packages.py       # native package CLI integration
```

## Registry packages

For a public Coven HTTPS mirror, set `[registry].protocol = "tuf"` and
provision the root and release trust files and their SHA-384 pins. Each
lock records one verified snapshot and the sealed target, release contents,
and publisher for each package. [HTTPS setup and verification](../coven/witchy2/tuf.md#consume-releases-through-grimoire)

For a legacy Coven server, declare its URL, operator and registry ID. The filesystem configuration below is also supported for existing local registries. [HTTP configuration and commands](docs/coven-http.md)

```toml
[registry]
path = "../../registry"
operator = "witchy-2:..." # the registry operator's key ID, whose key signs its snapshot
id = "example"            # the registry identifier its snapshots name

[dependencies]
config-reader = "0.1.0"
```

- **The registry snapshot.** Every resolve (`lock`, `run`, `review`) first verifies the registry's snapshot through Coven (`coven verify-snapshot`), keeps its bytes, and fetches every package against that one snapshot. The snapshot is signed by the registry's operator, whose key no publisher holds. Coven's README describes the format, and the operator's `coven snapshot` and `coven rotate-operator`.
  - **One suite, witchy-2 (the approved profile of 20 November 2026).** The operator signs snapshots and operator rotations, and package owners sign releases, indexes and rotations, with ML-DSA-65 in the engine (Coven's `witchy-2` suite). Every key is pinned by its key ID, `witchy-2:` and the SHA-384 of its 1952-byte public key, which `coven key` prints; every digest is `sha384:` and 96 hex digits. The suite and the algorithm are part of each pin, so no pin of an older suite stands for a new one, and none is compared as another algorithm's.
  - **Old locks are refused whole, not migrated.** A `witchy.lock` with any `sha256:` digest (package or `[toolchain]`), an SSH-fingerprint or `witchy-1:` signer or recovery key, or a `[snapshot] operator` of either is refused by `run` and by `lock` alike: "was made before the witchy-2 profile ...: Remove it and lock again (`grimoire lock`) against a witchy-2 registry, declaring the new keys in witchy.toml". Why whole: none of its pins can verify a witchy-2 registry (the registry itself must be republished, Coven's README), and dropping some of them silently on a relock would be a downgrade. The author removes the lock on purpose and anchors the new keys (`[registry] operator`, `[owners]`); `[registry] operator` or `[owners]` of an older suite is refused with the same pointer. This machine's trust store records of older-suite keys (an operator's, or a package's owners) are set aside as forgotten, with a warning: none of them can sign anything Coven accepts. The registry identifier is kept and a first use is refused, so a project must declare its keys. What an operator record of older-suite keys holds of witchy-2 keys (keys before the record and the keys each may hand the role to, unestablished keys, a witchy-2 key's floor, the unkeyed floor) is kept and migrated as any record without provenance (below); only the older suite's keys, floors and single floor go.
  - **The operator key is granted, never assumed.** It is anchored by `[registry] operator`, or by the lock's `[snapshot] operator`, which `grimoire lock` writes. Each comes with the registry's identifier (`[registry] id`, the lock's `[snapshot] registry`), which every snapshot and operator rotation names, so a snapshot that the same key signed for another registry is refused. The project's identifiers must agree with each other and with the one this machine recorded. Without an anchor, the resolve is refused, and the refusal prints the `operator` and `id` lines to check with the operator and declare: on a machine with no record, those the registry names now; where this machine holds a record, its newest key and identifier (an earlier, unstolen key is fine: the chain from it is followed), never a key only the registry's files name; where it forgot one, none, to get out of band (review of 116d62f: after a forget the key printed was the thief's, and pasting it locked onto it). `grimoire lock --trust-first-use`, the same opt-in as for owners, instead trusts the operator the registry names now and reports it. This machine's trust store never stands in for the project's anchor. A record that a project's anchors made (not a first use) cannot tell whose witchy.toml or lock that was, so it only ever refuses: a later `--trust-first-use` resolve is refused rather than anchored on it, and a project whose anchor contradicts it is refused as a fork (`grimoire trust --forget-operator` if this machine's record is the wrong one). A cloned project's operator pin, with a registry writer serving that key's snapshot, therefore neither vouches for a first use nor replaces your own project's record (final-state review; review of 101f2b4). A first-use record is replaced by a project whose anchor contradicts it. The rule, on every path: no project's anchors ever create, replace or promote a trusted operator record. Every record a resolve makes is `provisional` and stays so; the operator record is a floor, a list of retired keys and a chain that only refuses, and the anchors always come from the project. Its `source` (`first-use` or `project`, shown by `grimoire trust` as `(first use)` or nothing) decides only which refusals apply. Decision (review of ef0fdb0): an anchored resolve never prepends keys to a first-use record it does not contradict, and never changes its source. A cloned project that declares a registry writer's key W, with the writer serving W -> A beside A's honest snapshot, locks, but W -> A verifies for that resolve only: links the record never saw come with the project, whose anchor is granted by that project alone and is not assumed for this machine. Prepended, W made the record the project's, and an honest `--trust-first-use` was refused until the user forgot it. The resolve still records what follows the record's newest key, which a first use from that key verifies too, and raises its signer's floor. Decision (review of 83604b5): a link before the record's first key fixes no successor. Each is signed by the key handing on, but that key may be stolen, and only the project's anchor, perhaps a cloned project's, vouches for the link: with A -> B honest and a first use from B, a thief holding A served A -> T -> B beside B's snapshot, and recording A's successor as T made your own projects declaring A refused as a fork by a stolen key, past `--forget-operator`. Such keys are kept as before the record (`grimoire trust` lists them). An anchor on one does not contradict the record, so a stolen A's chain to a thief, without the record's newest key, is refused as a fork instead of replacing the record (review of 40b6650: A was unknown to the record, and a stolen A handed the role on). Successors the record's own chain shows retire their keys as before. A key before the record signs nothing, and hands the role only to a key the store keeps with it: the keys after it in the first chain that showed it, and the record's keys at that time (review of c411620: the record's alone refused an honest A -> X -> B the next time). The first chain may be a thief's: a stolen A shown first as A -> T -> B makes an honest A -> X -> B refused, and the project declares the current operator. To any other key it hands the role to no one, so a stolen one can neither hand the role to a thief while that record stands nor, after a replace, directly into the record that replaced it (review of d439eca: A -> W, W the replacing cloned project's key, made your projects declaring A the writer's). Decision (review of 0f9fae6): no record takes keys before its first one, a project's included: it cannot tell whose project's anchor vouched for them either, and prepended, a thief holding a replaced record's newest key B served B -> T -> C (or A -> B -> T -> C, review of c411620) and B was retired to T past a forget. They are kept before the record. The cost: after a forget, a project declaring or locked to an older key, an existing lock's `run` included, is refused until it declares the current operator and relocks. Decision (review of 7228c51, by the Witchy ethos: authority is granted, never assumed, and checks fail closed): no project's chain fixes a successor, on create, replace or extend. A successor is recorded only from links between keys of this machine's own record, verified in a resolve that extends that record. On extend those are the links from the record's newest key on (the first signed by that key, each later one by the key before it), from whichever resolve shows them first, a cloned project's included: a stolen current key signs snapshots anyway, and this is that case. A store written before this decision could hold successors and a whole key chain a project's chain fixed, which `--forget-operator` did not clear; such a record is set aside on load (see "Records an earlier Grimoire wrote"). A record a resolve creates or replaces holds only the key that signed its snapshot, and every key the chain shows before it goes before the record, under the rules above. Taken whole, a chain from a stolen key B never seen retired here (B -> T served to a cloned project declaring B, on a machine with no record, after a forget, or replacing a first use) fixed B's successor as T, and your projects declaring B were refused past a forget. The cost, accepted: after a forget, a project declaring or locked to an older operator key, `run` with an existing lock included, is refused, and the refusal names the fix: check the current operator with the registry's operator and declare it in [registry] operator with its id. The refusal names a key to declare only from this machine's record (its newest, which came from a first use or a project's anchor, so it is still checked with the operator); with no record it names none to declare, since the refused chain and its signer may be a thief's, and says to get the key ID and identifier from the registry's operator out of band (review of e77e23b: it named the signer as the key to declare). Then remove witchy.lock if it pins an older key, and `grimoire lock` again. A store that lists these keys without their record (written between 5f467cd and d439eca) retires them with an unknown successor. A replaced record keeps them before it, and `--forget-operator` retires them with an unknown successor: each then hands the role to no one, so a project declares the current operator, not a key only seen before a first use (review of 5f467cd: dropped with the record, a stolen A handed the role on again). Retired at a replace too, a project declaring the honest current operator, a cloned one included, made every project declaring A refused (review of 88a58ca). The cost that remains is a project still declaring A re-declaring the current operator after a forget, which the user chose: the price of never fixing a successor that only a project's anchor vouched for. The record is still replaced by a project whose anchor contradicts it outright, a writer's key with its own snapshot and no link to the record, as above.
  - **Each index.** Each package's index must be the one the snapshot lists, by digest and sequence. A package the snapshot does not list is not published yet, and neither is a version its listed index does not have. Both are refused until the operator's next snapshot, while a lock of earlier versions keeps running.
  - **Floors.** The snapshot must be signed by the operator the anchor reaches, through rotations each signed by the outgoing key, and must not be expired. It must also be no older than the lock's `[snapshot] sequence` and this machine's snapshot floor for its signer. So a registry writer cannot mix indexes from different snapshots, freeze the registry past the snapshot's expiry, or hide a newer index from a machine or lock that has seen a newer snapshot, even for a package that machine has never fetched.
  - **Floors per operator key.** This machine keeps a snapshot floor per operator key: the highest snapshot sequence verified signed by that key. A snapshot must be no older than its signer's floor, and only the signer's floor rises. Checking or raising the floors of the other keys of the chain let a stolen, retired key poison them, through a fork to a thief or a snapshot of its own on a machine with no record, for every chain through that key (reviews of 6b97913 and 7cfc468). A successor's newer snapshot cannot be hidden behind an older key's either way: the chain must still contain the newest operator this machine verified, and the older key's rotation away from it retires it. Decision (adversarial review of e2280af, and review of its first fix): a cloned project that declares a registry writer's key, with the writer serving that key a snapshot at 2^40, made the machine's single floor 2^40 for every project, past `--forget-operator`. A floor is authority over which snapshots a chain may present, and it is granted only by a chain holding its key: the writer's floor never constrains a chain without the writer's key. An honest key's floor is kept through a replaced record, a migrated one and `--forget-operator`, so an older snapshot of an honest operator is still refused after each, even for a project with no lock. A floor kept under a key nobody uses is harmless.
  - **Operator rotation.** It is followed from an anchor and recorded by the next lock. Every operator key this machine saw hand the role on in its record's own chain is retired, with the successor it handed the role to. A key seen only before a first-use record's first key is kept as before the record instead, with no successor (see above), kept through a replaced record, and retires with an unknown successor when the record is forgotten. A retired key is never accepted as a signer again, and a verified chain in which it hands the role to any other key is refused, on every path: a first chain, a replaced record and an extended one. Checking only the signer let a stolen retired key hand the role to a thief after `--forget-operator`, or where a first use's chain never held the anchor, since then no stored chain was there to fork from (review of ef0fdb0). The successor this machine saw binds even where it came from a fork: a cloned project that showed this machine a stolen key's hand-over first makes the honest hand-over a fork too, and your project then declares the current operator, which starts the chain after the stolen key. This machine keeps the longest operator chain it verified. A chain that does not contain the newest operator in it is refused as a fork or a rollback, even when the registry serves a shorter chain or none, unless that operator came from a first use that a project's anchor now contradicts: none of the anchors is in the chain the first use verified. An anchor inside that chain confirms it, so a stolen, retired key cannot hand the role to a thief and have a declaration of that key make the fork this machine's record. Because the check runs forward from the first anchor, a project that declares a newer operator than this machine holds is refused until the machine verifies the rotation: this fails closed.
  - **Forgetting.** `grimoire trust --forget-operator` forgets which keys are anchored, keeping each key's floor and the retired keys with their successors. The keys before the record retire with an unknown successor: they hand the role to no one, so a project declaring one is refused and declares the current operator. A project must then anchor the operator again, for example after an operator key is stolen and replaced. A first use (`--trust-first-use`) or a cloned project's declaration under a hostile operator can plant a very high snapshot floor, but only under the hostile key, so it refuses nothing your own operator signs.
  - **One act per `grimoire trust` call.** Re-establishing or reinstating an operator key (`--reestablish-operator`, `--reinstate-signer`, which may go together), `--forget-unkeyed-floor`, `--forget-operator` and `--forget NAME` are separate acts. A call naming two of them is refused and changes nothing; previously the first returned and the rest were silently not done. A refused `--reinstate-signer` (a key not refused for signing, or unknown) saves nothing, including the same call's `--reestablish-operator` (`TrustCommand` in `tests/test_operator_record.py`).
  - **Records an earlier Grimoire wrote.** An earlier record lists its retired keys without their successors. Each successor the record's chain still shows is kept. Where it shows none (the record was forgotten, or a first use was replaced), the key stays retired and may hand the role to no one: a chain in which it hands the role on is refused, and the project declares the current operator. An operator record without `source` (written before e2280af) migrates as forgotten, with its floor (its keys and retired keys become unestablished, below): those versions marked a record that a project's anchors made `provisional` too, so nothing tells it from a first use, and a cloned project's writer key would otherwise be what `--trust-first-use` anchors on (adversarial review of e2280af). An earlier record's single floor (`snapshot`) moves onto each key the record held. A record forgotten before the upgrade (`--forget-operator` up to e2280af kept the floor and dropped the keys) holds no key, and dropping its floor let an older snapshot through. Decision: it is kept as an **unkeyed floor**, which binds every chain's snapshots, as the single floor did then, and is shown by `grimoire trust`. It is not moved onto the next chain a resolve verifies: that may be a cloned project's writer key at 2^40, and the honest key would then have no floor. It is dropped only explicitly, by `grimoire trust --forget-unkeyed-floor`, which the refusal names: when the operator restarted its sequence under a new key, or the forgotten record came from a compromised registry. Such a machine refuses no more than it did before the upgrade. A project declares the operator again.

    Decision (settled with Astra): a record that cannot establish where its operator keys came from has the operator pinned again. Every operator record is now written with a provenance marker (`"provenance": 2`: its keys came only under the rules of e77e23b and later and of this decision; a record marked 1, written while this decision was being settled, keeps its chain and every retirement with a known successor, since those came from this machine's own record under e77e23b's rules; its keys set aside before the record with none to hand the role to retire with no successor, and a retirement from or onto an unestablished key keeps its key retired with no successor, in any marked record). Before e77e23b a project's chain could fix operator successors here and set a whole `keys` chain, and nothing in such a record tells those from links this machine's own record verified, so a stolen key's history (A handing the role to a thief T, from a cloned project declaring A) refused your projects pinned to A past `--forget-operator`. A record without the marker is migrated once, on load by any command, and saved marked: its keys are dropped, and every key it named (its chain, its retired keys and their successors, the keys before it, and the keys of its floors, which an earlier forget kept without the keys) is `unestablished`. Each successor it recorded (its chain's links, its retirements, `None` among them, and its keys before the record with the keys each could hand the role to) is kept as a constraint on where that key may hand the role on (`grimoire trust` shows "may hand the role only to"): no migration weakens a constraint (decision, by the coordinator). Where a key has several (a retirement, a chain link, a `before` list), it may hand the role only to a key all of them allow, to no one where they share none. A `before` entry that is not a list refuses the store. A key the record held retired, before it, or anywhere in its chain but last (which by the record's meaning handed the role on) also keeps the refusal to sign it had there (`grimoire trust` shows "sign nothing"), pinned or not: after an honest A -> B, a thief holding A signing alone is refused for a project whose lock pins A (decision, by the coordinator). `--reestablish-operator KEY` does not lift it: an operator asked "was A ours?" truthfully says yes for a key stolen after it handed the role on. Only `grimoire trust --reinstate-signer KEY` does, after checking with the registry's operator that KEY is still its current signing key, and only for a key already established (or re-established in the same call: `--reestablish-operator KEY --reinstate-signer KEY`). Neither lifts the hand-over constraint. A chain in which such a key hands the role to any other key is refused, pinned or re-established, naming no key, and the refusal says to pin the current operator directly. Such a key is accepted only where this project pins it explicitly, by `[registry] operator` or the lock's `[snapshot] operator`: never through `--trust-first-use`, an extend of the record, or a chain the registry's files or a cloned project imply (a thief's A -> T, T named by the old record, is refused for a project pinning only A). It never fixes a successor, and none is fixed onto it: a key of the record that hands the role to one retires with no successor (it signed the hand-over, but only a pin accepted the key it handed to). `--forget-operator` retires an unestablished key that was before the record with no successor, as any key before the record, and every key of the record that handed the role on with no successor recorded (an unestablished key's hand-over), without naming an unestablished one: otherwise the forget the fork refusal advises let a thief's chain from it pass. No load, migration or forget of a marked record ever weakens a constraint this machine recorded: it only adds constraints or changes wording (review of a7a0169). A pin re-accepts only an unestablished key, never a retired one: a key retired to a known successor stays refused handing the role to any other, pinned or not. The pin is the re-pin, for that project's resolve only: the resolve may start a fresh, marked record on it under the rules above (it holds only the signer), carrying the old record's hand-over constraints but no successor of it, but the key stays unestablished for every other project, since a project's anchors never change this machine's trust record (a cloned project's pin would otherwise clear the mark for all of them). Only the user re-establishes a key for the machine, with `grimoire trust --reestablish-operator KEY`, after checking it with the registry's operator out of band. Its floors are kept, each key's and the unkeyed one, and `--forget-operator` keeps the unestablished keys. The refusals name no key (none was verified independently of that record): they say to get the current operator's key ID and the registry's identifier from the registry's operator out of band, pin them, remove a lock pinning an older key, and lock again. `grimoire trust` lists those keys as unestablished. The cost, accepted: on every machine with such a store, the first resolve of each project without an anchor is refused until its operator is pinned; a project pinning an older key whose chain reaches an unestablished key it does not pin is refused until it pins the current operator or the user re-establishes that key (a key the old record named as a successor, the honest current one included, is unestablished too, so a project pinning A locks on a recorded A -> B only with B pinned as well); and where the old record holds a successor a thief planted (A -> T), the honest A -> B is refused for every project pinning A, which pins the current operator B directly. The honest current key has no recorded successor, so a pin on it works with no rotation; one the old record held retired (a thief's planted A -> T) signs only once the user re-establishes it and reinstates it as a signer.

- `grimoire lock` in a project with no `[dependencies]` and no `[registry]` has nothing to lock and says so; `grimoire lock --toolchain` there pins the compiler and the engine alone.
- `grimoire lock` resolves the whole graph through Coven: each version's verified record lists its own exact requirements. It writes every package's version, content digest (`sha384:<hex>`) and requirements to `witchy.lock` beside the manifest. A version already pinned keeps its digest, and if the registry now has other bytes for it, the lock is refused. Two versions of one package are refused, naming both chains.
- `grimoire run` then needs a lock that pins exactly the graph the dependencies require. It fetches each package through Coven, which refuses a copy whose digest differs from the locked one, before anything is compiled. The app's `.wy` files are staged with a generated package list naming the verified copies. Its grants still come only from its own manifest and document. Its policy (`main.policy` for `main.wy`) is staged with them. A policy is required whenever the program has packages, from the registry or a checkout. The policy names each package as `@name`, wherever its copy is.
- `grimoire review --write-policy` writes the drafted policy beside the entry when there is none, or in place of the one `grimoire new` wrote while that is still exactly the scaffold (nobody reviewed it); an edited policy is replaced only by `review --write-policy --replace`. It accepts nothing for you. The draft pins by digest the code the author did not write (each `<standard>/` file and each package file) and leaves the project's own files unpinned: `main.wy: Console<Write> ; no unchecked`. An own file is held by the capabilities on its line, which every build applies, so an edit that uses nothing new builds with no further command and one that reaches further is refused until the author edits the line (or drafts again with `--replace`). A digest on an own line is still honoured and kept current by `review --accept`, for an author who wants each edit acknowledged. Decision (2026-11-22): a pin answers "is this the text that was reviewed?", a question about code that arrives from elsewhere; for the author's working file it added a command after every edit and no authority check that the capability line does not already make. The gate on registry packages is unchanged: every file of every locked release needs a line with a current digest. The compiler refuses a program with a file in no line of the policy, the project's own second file included (`consts.wy is in no line of the policy`): the draft gives each of the project's files a line without a digest, which holds it, and `review --accept` writes a pinned `nothing` line for each release file that holds no function `main` reaches (told from the compiler's by-file listing). When a pinned package's source is no longer the accepted text, `review` and `review --accept` say first what changed: `@notes-core 0.1.1: 4 lines added, 0 removed in 1 place since the accepted source; in: release_marker`, then `compare: diff -u OLD NEW`, the two full texts. Grimoire keeps a copy of each package source a review has shown, named by its SHA-384 under `$XDG_STATE_HOME/grimoire/sources`; a copy is read only if it still hashes to its name, and where none was kept (accepted on another machine) the review says so and names the new source to read whole.
- A version the snapshot's index does not list is refused by Coven; Grimoire adds what that usually means: the registry's operator has not yet signed a snapshot that includes it (`coven snapshot`), or it was never published.
- Diagnostics name the author's files, and are read in either compiler's format (`PATH:L:C: W0401: message`, or the earlier `W0401 12..19: message`). Builds read staged copies (a library's release bytes, a registry consumer's app beside its generated package list, each verified release unpacked into a fresh source directory and shown under `@NAME-VERSION/`, a test suite); what the compiler says of a copy is printed with the path it was copied from.
- A library may be several files: `[package].source` and the `.wy` files of its own directory it imports (lower-case ASCII paths, at most 64 files, 1 MiB in all). One signed release covers every file, the lock pins the whole release, and each file is checked against its listed SHA-384 before the compiler sees it. A package of one file is published exactly as before, with the same digest. The compiler names the entry `@NAME` and the others `@NAME/PATH`; a policy holds them file by file or with one `@NAME/:` line. Every file of every locked release must be held by a policy line with a current digest, whether or not `main` reaches a function in it: `run`, `build` and `test` refuse otherwise, `review --write-policy` drafts those lines and `review --accept` pins them. `review` lists every file of such a release and, on an update, each file added, removed or changed since the accepted digests. [Format, path rules and decisions](docs/multi-file-packages.md)
- `grimoire review` shows what each file of the locked program uses, checked against the policy, and what a run would be granted: a `grant:` line for the listener's address, the directory with its rights, the clock, each secret with its use and source (never a value), output and memory, and a `limit:` line for each run limit. The lines are made from the flags Grimoire would pass the engine, after its own checks and after anything it withholds or adds, so a document `grimoire run` would refuse fails the review with no grant shown (the policy is still compared, and `--accept` still pins it), and a flag with no description is printed as it is. A secret is shown with its default source; `--bind` and the check of a granted file against the secrets' sources belong to `run`. `grimoire run` and `grimoire build` print the same lines on standard error before anything is built. After reviewing an update, `grimoire review --accept` pins the policy's digests to the new code. It changes no capability.
- Each package keeps its owner. The lock records each package's owner key (`signer`, a `witchy-2:` key ID, or `unsigned`) and its recovery key (`recovery`), from Coven's package index. Coven then admits only a package owned by that key, or handed on from it by a rotation signed as the package requires. A package that is unsigned after being signed is refused until the author removes it from the lock on purpose. A rotation is reported on runs, and the next `grimoire lock` records the new owner. `[registry] signed = true` refuses unsigned packages.
- The lock records the sequence of each signed package's index (`index = N`) and passes it back to Coven, so a registry serving an older index (one from before a yank or revocation) is refused. An expired index is refused too.
- **Declared owners.** The project's author can declare each dependency's owner in `witchy.toml`, independently of the registry:
  ```toml
  [owners]
  config-reader = "witchy-2:..."
  other = { owner = "witchy-2:...", recovery = "witchy-2:..." }
  ```
  A declared owner anchors the package, and the verified owner chain must contain every anchor: the declared owner, and the lock's pin if there is one. A declared recovery key must match the lock's and the one this machine verified. A brand-new machine resolving the project therefore trusts nothing on first use. Trust on first use is never the default. `grimoire lock` refuses a signed package that the project itself does not anchor, with a declaration or a lock pin. This machine's trust store never stands in for them, because a record cannot tell whose project made it, and a cloned project's files would otherwise vouch for yours. The refusal prints the `[owners]` line that would anchor it, so the author can check that key ID with the publisher and declare it. `grimoire lock --trust-first-use` instead trusts the owners the registry names at that moment, and it names each one it took, with its `[owners]` line. `[registry] owners-required = true` goes further: it refuses an unanchored package even with `--trust-first-use`.
- **Rotation after a key theft.** A declaration or lock that still names a stolen, rotated-away owner keeps accepting that owner on a machine that never saw the rotation. After a recovery, update `[owners]` to the new owner, or lock again.
- **Rotated-away keys.** Every key this machine has verified handing a package on is retired. A retired key is never accepted as the package's owner again, across projects, stale locks and `grimoire trust --forget`. That one rule is the protection against rollback by a stolen old key.
- **Forks.** A verified chain must contain the newest owner this machine verified, so a fork or rollback is refused. The exception is a first use whose chain does not contain the owner a lock or declaration names. There the anchored chain replaces what the first use taught, and the replacement is itself still treated as a first use: one project's files do not become this machine's trusted record until a later anchored resolve extends it. A first use whose chain does hold the anchor keeps its retired keys and is checked like any other entry. `grimoire trust` shows each package's owners, retired keys, floor and whether the entry came from a first use. `grimoire trust --forget NAME` drops its owners but keeps its retired keys, floor and known revocations, and then requires a lock or declaration to anchor it again. Every retired key was verified under the package's recorded recovery key, and a package's recovery key never changes. So when a lock or declaration re-anchors a forgotten or first-use entry and states a different recovery key, all its retired keys are dropped: a poisoned record cannot keep the honest owner refused. A trusted entry that the project contradicts this way is refused until it is forgotten.

  Two limits remain, both found in review of 3d3f7d5:
  - **Forget, under recovery `none`.** For a package without a recovery key, the owner keys sign the hand-overs. After `--forget`, a thief holding a rotated-away key can sign a hand-over to a new key, and a stale lock pinning that old key accepts it. Without the forget, it is refused as a fork. Forgetting the hand-overs is what lets `--forget` undo a poisoned first use. A package with a recovery key is not affected, because only the recovery key signs its hand-overs. Publish with `--recovery-key`.
  - **A planted floor after a theft of the current key.** A thief holding the current owner key can sign a valid index with a huge sequence. This machine accepts it and raises its floor, and `--forget` keeps the floor. The honest recovery must then publish above that sequence (Coven's `rotate --min-sequence`). The thief's index records the number. Forgetting it lets the project's stated recovery key replace this machine's record, so check that key with the publisher first. An entry becomes trusted only through a lock or declaration that states the recovery key; a bare declaration accepts its declared owner alone and does not follow rotations a first use recorded.
- **The trust store.** This machine keeps what it has verified of each registry in a trust store, `$XDG_STATE_HOME/grimoire/trust/` (default `~/.local/state`), held under an exclusive lock while a graph resolves. For each signed package it records:
  - the verified owner-key chain, which only grows;
  - the recovery key;
  - the highest index sequence verified (a floor);
  - the retired keys;
  - whether the entry came from a first use.

  It also records the versions seen revoked, and the registry's operator: its verified key chain, the keys retired from it with the successor each handed the role to (or none known), the keys seen before a first-use record's first key, the highest snapshot sequence verified per operator key (floors, see "Floors per operator key"), and whether it is provisional, with the provenance marker (see "Records an earlier Grimoire wrote"). All of this is kept across projects and lock deletions:
  - Deleting a lock does not lower a floor.
  - A second project trusts the same owner.
  - A revocation seen here stays refused even if the registry later serves a valid index that lists the version as active again.

  A floor or revocation from a refused fetch is kept only when the fetch was checked against an anchor or a stored owner. A first use that is refused records nothing, so a registry cannot plant a lasting revocation. A first use can still plant a very high floor, which is denial of service and not forgery; `grimoire trust --forget` or moving the store aside recovers. A store Grimoire cannot read is refused; move it aside to start again. An entry an earlier Grimoire marked conflicted migrates as forgotten.
- A version its publisher has yanked is refused for new locks and kept, with a warning, where a lock already has it. A revoked version is refused everywhere (Coven's `yank` and `revoke`).
- `grimoire lock --toolchain` also pins the compiler and the host by SHA-384 (`sha384:`) in `witchy.lock`, and the libraries the host loads from its own directory (the AWS-LC FIPS crypto module, a separate file on macOS) under `[toolchain.host-libraries]`. A plain relock keeps the pin. Every command that compiles or verifies (`run`, `lock` and `review`) then refuses any other compiler or host before compiling or verifying anything; only `lock --toolchain`, which re-pins on purpose, does not check the old pin (final-state review: `lock` and `review --accept` ignored it).

## When Grimoire itself fails

No command ends in a Python traceback. A failure no command expected is a defect in Grimoire: it is one line (`grimoire: stopped by a defect in grimoire itself (AttributeError: ...); nothing further was done.`), status 70, and nothing the command had not already done is done. `GRIMOIRE_DEBUG=1 grimoire ...` shows the traceback for a report; the variable is read once at launch and is not passed to the compiler, Coven or a run.

A step that derives a key or has Coven verify a registry for the first time takes 5 to 25 s, because Coven's own programs are compiled and proved on first use. After two silent seconds `keygen`, `lock` and `publish` print one line on standard error (`grimoire: deriving the ML-DSA-65 key pair with Coven (still working: a first use can take half a minute)`); a step that finishes sooner prints nothing.
