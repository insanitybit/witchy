# Coven for Witchy 2

Use `coven serve --store STORE --port 8787` to run the registry, and `grimoire publish` and `grimoire lock` from projects. The following local commands describe the underlying signed objects and administrative rules. [HTTP service, bootstrap and restart](service.md)


For private uploads and approved releases, see [CI staging](ci-staging.md) and [Coven releases over TUF](tuf.md).

The original filesystem interface remains available for private administration and local-registry fixtures. Its decisions are Witchy 2 programs that run in Wasmtime with only the paths they need. `coven` is the Python host bootstrap that grants them those paths.

```sh
export WITCHYC=/path/to/witchyc WITCHY_WASMTIME_HOST=/path/to/witchy-wasmtime-host
# A witchy-2 key (a package owner's, a recovery key, the registry operator's): a 32-byte seed only its owner reads
(umask 077 && head -c 32 /dev/urandom > owner) && ./coven key --key owner   # writes owner.pub, prints its key ID
./coven publish path/to/package --registry REGISTRY [--key owner [--recovery-key rescue.pub]]
./coven fetch NAME VERSION --registry REGISTRY --into DIR [--expect sha384:<hex>] (--operator witchy-2:<hex> --registry-id ID | --no-snapshot)
./coven snapshot --registry REGISTRY --key operator (--first --id ID | --min-base N)  # first, then later snapshots; or --key fd:N --public-key operator.pub; a served registry (URL or server store) also needs --admit NAME for each first claim it lists
./coven rotate NAME --registry REGISTRY --key owner --new-key next (--operator witchy-2:<hex> --registry-id ID --min-snapshot N | --no-snapshot)  # without a recovery key
```

- **Package manifest:** a package's `witchy.toml` has a `[package]` table with `name`, `version` (exact MAJOR.MINOR.PATCH) and `source` (one `.wy` file inside the package directory). It may also have `[dependencies]`, `name = "MAJOR.MINOR.PATCH"`, each of which must already be published.
- **Layout:** `REGISTRY/NAME/VERSION/{package, source.wy, digest}`. `package` is the canonical record (`witchy-package 1`, `name`, `version`, one `requires NAME VERSION` per dependency in name order, then a blank line). `digest` is `sha384:<hex>` of `package` followed by `source.wy` (at most 1 MiB together). A package of several files is `witchy-package 2`: after the `requires` lines the record has `entry PATH` and, in the byte order of their paths, one `file PATH LENGTH sha384:HEX` line per file (2 to 64); `source.wy` then holds the files' bytes in that order and nothing else. One file is always format 1 and several always format 2, and a record is accepted only if writing it again from its fields gives the same bytes, so a set of files has one release and one digest. Paths are lower-case ASCII, relative, `.wy` only; every file must be reached by the entry's imports and no import may leave the release. `witchy_release.py` (pinned by SHA-384 in `coven`, shared byte for byte with Grimoire) is the one reader and writer: `pack` and `publish` read the package's directory by handle without following links, the server parses every upload before any other check, and `fetch` parses the slot before copying and the kept copy after. The per-file digests are SHA-384, the suite's digest: they sit inside the bytes the release digest covers, so another algorithm would add a second check and no strength. Specification and decisions: Grimoire `docs/multi-file-packages.md`.
- **`publish.wy`:** reads the bundle (record, then source) once into memory, hashes it with the engine's SHA-384 (AWS-LC), and stages those same bytes, split into the two files; then it claims the version by creating `digest` exclusively. Of two racing publishers, exactly one wins. Republishing identical source stores it again, which completes a publish that stopped after its claim. Different source is refused.
- **`fetch.wy`:** first verifies every signature the fetch's decision rests on (see "Verification" below) and reads nothing of the slot unless each is valid. It then reads both files once, hashes them with the engine's SHA-384, and keeps those bytes in `DIR/package` and `DIR/source.wy` only when their hash equals both the registry's record and the expected (locked) digest.
- **Grimoire:** `grimoire lock` and `grimoire run` use `coven fetch` for `[dependencies]`. See Grimoire's `examples/registry` for the end-to-end demo and its limitations.

Every program uses the standard library (`Vec`, `fs`, `crypto`), so Coven needs the proof environment (`WITCHY_WASM_READY_BINDING`, and for speed `WITCHY_PROOF_CACHE`; built modules and grant checks are cached per user, `build_module` and `witchy_flags`, in a directory and entries no one else can write, by mode, access control list or hard link, or else not at all; a grant check is cached on its document with each path replaced by a placeholder, put back in one pass, and a document whose paths look like placeholders is checked as it is), and an engine with AWS-LC's FIPS module and the witchy-2 suite: Witchy 2 `f951b90f` or later, its `libaws_lc_fips_*_crypto.dylib` beside the host. The package programs used to avoid the standard library and hash in Witchy code (a streaming SHA-256); the profile's digest is now the engine's SHA-384, so the bytes signed over come from the one validated module.

Coven caches modules and grant checks only when it uses a macOS compiler session to identify the full source graph. Standalone compiler invocations, including wrapper scripts, build the module and check its grants on each request.

```sh
grimoire test witchy2                         # default Witchy package suite, from the repository root
python3 witchy2/run_tests.py                  # host policy, parsing and integration
python3 witchy2/run_tests.py --engine-boundaries  # signing pipes, command verification, large batches and independent provider
python3 witchy2/run_tests.py --all            # run both host groups under one five-second limit
python3 witchy2/run_tests.py --all --packages # include the Witchy package suites in that limit
```

For the timed host suite, build the Witchy Wasm host with `--features resident`
and set `WITCHY_WASMTIME_RESIDENT` to that executable. Also keep
`WITCHY_WASMTIME_HOST` pointed at the ordinary host build. The test-only
resident engine reuses compiled Wasm and forks a fresh process for each
invocation. The signed-registry and web-preview protocol cases can use it.
Tool wrappers, socket lifecycle checks, and `--engine-boundaries` use the
ordinary executable to exercise process startup and descriptor behavior.

**Symlinks.** A version's `NAME` and `NAME/VERSION` must be real directories. Every program's grant document says `[paths] links = false`, so the engine opens each granted path from `/` without following a link, using the descriptor it opened (Witchy 2 `7ce525cc` or later, for both the compiler and the host). A slot swapped for a link after the launcher's checks is refused, not followed. The launcher also refuses if a slot was replaced (device and inode) while its program ran.

**Cryptographic policy for new profiles (21 November 2026).** Target CNSA 2.0 and NIST post-quantum security Category 5 for signatures. For each new signing profile, compare ML-DSA-65 (Category 3) with ML-DSA-87 (Category 5) and prefer ML-DSA-87. A CNSA 2.0 profile using ML-DSA requires ML-DSA-87. Record any external interoperability constraint and the FIPS-approved algorithm used at that boundary. The shipped `witchy-2` suite identifies ML-DSA-65 with SHA-384. Moving to ML-DSA-87 requires a distinct suite identifier, new signing keys and matching verifier support. [FIPS 204, §4](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.204.pdf) · [NSA CNSA 2.0 FAQ, p. 3](https://www.nsa.gov/Portals/75/documents/CNSA%20Suite%20documents%2009-2026/CSI_CNSA_2.0_FAQ_.pdf)

**Hash choice.** Default to SHA-384. Consider SHA-512 for every new digest use and record the reason for the choice. CNSA 2.0 permits both at every classification level. When a protocol requires 256-bit classical collision resistance for the digest itself, use SHA-512. SHA-384 provides 192 bits and SHA-512 provides 256 bits. Identify the hash in the signed profile so the verifier enforces that choice. [NIST hash strengths](https://csrc.nist.gov/projects/hash-functions)

**The witchy-2 profile (20 November 2026).** Every role signs with one suite, `witchy-2`: ML-DSA-65 (FIPS 204) in the engine (Witchy 2 `import crypto`, AWS-LC's FIPS module; no FIPS claim is made, see the compiler's `docs/decisions.md`, 2026-11-20), SHA-384 (FIPS 180-4) for digests and key IDs. The roles are the operator's `snapshot` and `operator-rotation`, and the package owners' `release`, `index` and `rotation` (the recovery key signs `rotation` objects too). Nothing of the suites before it is accepted.
- **Objects.** A witchy-2 object is its canonical bytes, beginning with its role's domain `witchy/v2/ROLE\0` (AWS-LC's ML-DSA takes no context string, so the domain is inside the signed bytes), then one line `signature <base64 of 3309 bytes>`. The body names the suite (`suite witchy-2`) and its signer's whole public key (`signer witchy-2 <base64 of 1952 bytes>`, or `operator`/`from` for the operator's objects). A signature over one role's object never verifies as another's, and the engine's signer for one role refuses to sign the other's (`Err(WrongDomain)`): the role is the grant's (`sign/witchy-2/ROLE`), so one program, `sign.wy`, signs for every role.
- **Key IDs.** `witchy-2:` followed by the SHA-384 of the 1952-byte public key, in hex (96 digits). Why: an ML-DSA-65 public key has one encoding of fixed length (FIPS 204's pkEncode), so one key has exactly one ID with nothing to canonicalize (an SSH blob needed `canonical_key`, 9f6117f); the hash is over the bytes `witchy2_verify` is given, so the ID a client pins is the key that verifies; and the suite is part of the ID, so a pin names the suite as well as the key.
- **Digests.** `sha384:` and 96 hex digits: a version's digest, a snapshot's index digests, and Grimoire's lock and toolchain pins. The algorithm is part of the text, so a value is never compared as another algorithm's.
- **Keys.** A key is a 32-byte seed (FIPS 204's ξ), raw, in a regular file only its owner can read (yours, `chmod 600` and no ACL: an extended ACL that lets others read it is refused, and so is a link or a longer or shorter file), or on a descriptor coven was started with (`--key fd:N`, with `--public-key FILE`, for the operator's commands). `coven key --key SEED` (also `operator-key`) writes its public key (`SEED.pub`) and prints its key ID. Coven makes its decisions for the key the public key file names, and refuses to write anything if the engine's key is another.
- **Delivery, as Grimoire's secrets.** Coven reads the seed only when it signs, into a buffer it clears as soon as the seed is written to a fresh pipe of the engine's own (`--secret-slot=key:sign/witchy-2/ROLE:fd:N`, and `--secret-object` naming a seed file's device and inode, so no grant reaches it). The program, `main(key: Signer, ...)`, can sign only that role's objects and has no operation that reads the key. The seed is never in an argument, a variable, a grant document, a file Coven writes or the compiler's steps (which get no descriptors); the engine gets no environment. `test_the_operator_seed_reaches_only_the_engine` checks a canary for all of these.
- **Verification.** Each object is checked with `witchy2_verify` for the role Coven asks (a fixed list), domain included (`verify_batch` in `witchy2.wy`). A key or signature of another length, a message outside the role's domain, or any other suite is refused. Verification rides on the engine run that acts (`deferred`):
  - Coven decides as before, each object where it is parsed, but takes a signature it has not verified yet as valid for now and adds it to a batch. It reports nothing yet: what it prints is held.
  - The command's next engine run (`fetch.wy`, `publish.wy` or `sign.wy`) gets the batch as its input and verifies all of it first, printing a verdict for each. It acts only if every one is valid. Otherwise it reads, writes and signs nothing, and Coven drops what it held and decides the whole command again, now verifying each signature where it is read, in a run of `verify.wy` (as before this change), with the verdicts found so far.
  - A write with no engine run before it (`verify-snapshot --keep`), and the end of every command, refusals included, first verify what is still in the batch with `verify.wy`. Nothing is copied, written, signed or reported from a signature that was not verified. A record stays in the batch until its verdict is kept, so a run that stops leaves it to be verified; and a command that ends in an error reports only the error unless every record it took as valid has since been verified valid.
  - The batch is the program's input (`[input]`), granted exactly its size (`--input-bytes`) with fuel for it. A batch above 4 MiB is verified first by `verify.wy`, in runs of at most 4 MiB, and the program then carries none.
  - The signer verifies its own signature before it writes it, so an object Coven signed and reads back needs no run.
  - The facts Coven's decisions use (the snapshot's entries, the owner chain, the index's sequence, expiry and entries, the release's signer) are still decided in Coven, from the objects as parsed; the engine only answers whether each signature is valid.
  - Two exceptions. The `.index.lock` and `.snapshot.lock` files are taken before the run that verifies; they hold nothing and are removed on every exit. `fetch --into DIR` creates DIR (and its missing parents) for the run, since the engine is granted DIR itself, and removes them again if the run verified a signature as invalid.
- **No downgrade: what is refused, and what to do.** There is no installed base to carry over, so nothing is migrated: an object signed with ssh-keygen or in witchy-1's domain (`witchy/v1/`) is refused as `signed with ssh-keygen` / `signed with witchy-1 (ML-DSA-44)` wherever it is read (a release signature, an index, rotations, a snapshot, operator rotations), and a version recorded with a `sha256:` digest is refused with "this registry predates the profile; republish the package into a new registry". Publishing into such a slot, or requiring such a version, is refused the same way. A `--expect sha256:` is refused with "lock again"; an SSH fingerprint or a `witchy-1:` key ID given as `--operator`, `--expect-signer`, `--expect-recovery` or `--from-owner` is refused with a pointer to the key ID; an SSH or witchy-1 public key file is no key. The engine itself has no ML-DSA-44 any more.
- **Speed.** Owners sign and verify in the engine instead of ssh-keygen. Each engine run costs 35 to 50 ms, about 19 ms of it starting the host, so no command spends a run on verification alone: a fetch is one run (`fetch.wy`), `snapshot`, `yank`, `revoke` and `refresh` one (`sign.wy`), `rotate` and `rotate-operator` two, a signed publish three (sign, `publish.wy`, sign), and `verify-snapshot` one (`verify.wy`). A signature that does not verify costs a run or two more. `test_each_command_verifies_in_the_engine_run_that_acts` counts them. The tests use fixed synthetic keys (`test-keys/`) so that no test spends an engine run deriving one.

The legacy fetch worker verifies the package before staging either cache
file. It checks the coordinate, the exact boundary between the registry's
record and body, the digest approved by the launcher, and any lock digest.
For a multi-file release it uses the same Witchy decoder as the TUF workers
to verify file paths, file digests, and the complete import closure. The
launcher can read a refused package to explain the format error.

**Release signatures.** `publish --key KEY` signs a witchy-2 object of role `release`: `coven-release 2`, the suite, the signer's public key, the name, the version and the version's digest.
- **Stored once.** The signed object goes into `release-signature` by an atomic link, so a version keeps its first signer. Another key signing the same release is refused, and a signature already there is verified, not signed again.
- **Checked on fetch.** `fetch` checks the signature against the recorded digest before `fetch.wy` reads the slot (`fetch.wy` verifies it first, in its run), and the verified digest must equal it. It then prints `signed by witchy-2:...` or `unsigned`. A signature that does not verify for exactly that name, version and digest is refused, and nothing is kept.

**The package index.** Each signed package has `NAME/index`, signed by its owner: the key of its first signed release (namespace `coven-index`). It is a witchy-2 object of role `index` (`coven-index 2`). It lists every version with its digest and state (`active`, `yanked` or `revoked`), under a sequence number that grows with each change and an expiry date (30 days by default). These are TUF's targets and timestamp properties, for one owner key per package.
- **Ownership.** Once a package has an index, only its owner's key can publish to it. A publish by another key, or an unsigned one, is refused before anything is written.
- **Completeness.** `fetch` admits a version of an indexed package only if the index lists it with the same digest and the owner signed the release. A version stored around Coven is refused, and so is a signed version whose package has no index, because deleting the index would hide every withdrawal.
- **Rollback.** `fetch --min-sequence N` refuses an index older than one the client has seen. Grimoire records each package's sequence in its lock and passes it back.
- **Freeze.** An expired index is refused, which bounds how long a registry can keep serving a stale one to a client that never saw the newer one. The owner re-signs it with `coven refresh NAME --key KEY [--valid-days D]`.
- **Bounds (final-state review).** Every index is checked where it is signed and wherever it is parsed, so that no key, stolen or not, can sign one that outlasts the freeze bound or leaves the recovery key no room above it. Before these bounds, a thief with an owner key signed an index at sequence 10^18-1 expiring in 9999. The operator admitted it, and the recovery rotation would have had to sign at 10^18, which no snapshot line carries, so the thief kept the package for good. The choices:
  - An index is valid for at most 366 days (`MAX_VALID_DAYS`). One that expires more than 367 days after today (a day of clock skew) is refused.
  - A sequence is at most 2^53-1 (`MAX_INDEX_SEQUENCE`: exact as a double, and far inside the 18 digits of a snapshot line).
  - The operator admits a sequence at most 2^20 above the entry it had (`MAX_SEQUENCE_STEP`; 0 for a new entry). Every admitted sequence is therefore at most 2^20 times the number of snapshots signed: a thief needs 2^33 snapshots to reach the bound. A recovery rotation signs one above the admitted sequence, so it always has room.
- **The owner's copy.** Every update the owner makes builds on a copy of the last index their key signed, which is kept on their machine under `$XDG_STATE_HOME/coven/signed` (default `~/.local/state`). It does not build on whatever the registry serves. Otherwise a registry writer could put back an index from before a revocation, and the owner's next routine `refresh` would re-sign it under a higher sequence, undoing the revocation even for clients that had seen it (found by review). An index that was put back, deleted, or replaced with one under another key is repaired by the owner's next update, with a warning. A later index signed by the same key on another machine is accepted. The registry's index is trusted on first use only when this key has never signed the package on this machine.
- **First index.** A key cannot start an index for a package whose versions are signed by another key. The first index lists the versions this key already signed.
- **Serialized.** Updates to one package take an exclusive `NAME/.index.lock`. A registry writer can plant that file and block updates; this is denial of service, not forgery, and the owner deletes the file.

**Withdrawing a release.** `coven yank NAME VERSION --reason TEXT --key KEY` and `coven revoke ...` record the state in the package's index, re-signed by its owner. A yank does not undo a revocation.
- **What fetch enforces.** It refuses a revoked version always, for every client, before copying anything. It refuses a yanked one unless `--expect` gives a digest already locked; then it fetches it and reports `yanked: REASON`. Grimoire checks the same again.

**Rotation and recovery.** A package's first signed publish can name a recovery key (`publish --key KEY --recovery-key RESCUE.pub`). The index records its key ID (`recovery`, or `none`), and it never changes. `coven rotate NAME --key SIGNER --new-key NEW` hands the package to a new owner key in two steps. First, it appends a statement to `NAME/rotations`, a witchy-2 object of role `rotation` (`coven-rotation 2`): "the key `from` (a key ID) hands NAME to key `to` (its whole public key)". Second, the new key re-signs the index. The modelled threat is a stolen or lost key, as with TUF's root role.
- **Who may rotate.** If the package has a recovery key, only the recovery key signs rotations. A stolen owner key then cannot hand the package to a thief, and the owner of a lost key can recover the package. Without a recovery key, the current owner signs.
- **Whose word on the recovery key.** Rotations are checked against the recovery key a consumer pinned, or against the owner's own copy. They are never checked against the `recovery` line of the index the registry serves, because that line is signed by the end of the chain, which a registry writer can make their own key (review). `fetch --expect-signer` therefore follows rotations only together with `--expect-recovery`.
- **Recovering from a stolen owner key.** The recovery key's authority is its own key, which consumers pinned, so it can rotate even after a thief signs an index declaring `recovery none`. When it rotates:
  - it keeps only the rotation statements that are valid under it, dropping any the stolen key signed;
  - it hands the package on from the last legitimate owner;
  - it restores itself as the recovery key;
  - it signs above the latest sequence known (`--min-sequence`, or its base) and above the registry's index, unless that index is 2^20 or more above the known one: the operator would never admit it, so the rotation signs above the known one, with a warning.
  The recovery key's rotation is anchored outside the registry. `--from-owner` names the owner it hands the package on from, which a consumer's lock records as `signer`. The chain is cut at that owner, and the index the rotation starts from must be signed by it. Otherwise, a registry writer could delete the rotations, plant an index under its own key, and have the recovery key hand the package on from that key (review). The recovery key has never signed an index, so it also needs `--min-sequence`, the latest sequence known. It takes the registry's index only if that index is not expired and not older than this. Otherwise it takes `--from-index`, the owner's last copy. The rotation prints every entry it signs over. The owner's tool refuses a later index under its own key that changes the recovery key, a sign that the key was stolen.
- **What a rotation builds on.** Not only `NAME/rotations` as served: also each bound chain the registry keeps (`NAME/chains/HEX`, its bytes checked against the digest its name says), with the served statements after it. The rotation takes the one that reaches the owner it hands on from through the most statements, each verified as before. A writer who deletes or cuts `NAME/rotations` therefore does not make the next rotation write a chain that drops the bound one (adversarial review of 363f952).
- **Without a recovery key, on the chain the operator bound.** There, owner keys sign hand-overs, so a thief with an earlier owner key can sign a second chain to the current owner through a key of its own (`[alice->mallory, mallory->bob]` beside the bound `[alice->bob]`). Built on the longest chain reaching bob, bob's rotation to carol extended the thief's, which the operator never admits: the package froze at bob, and carol's updates were never admitted (review of dd42df8, reproduced; possible before it too). The owner's rotation now builds only on rotations that extend the chain the pinned operator's snapshot binds for the package: `rotate --operator KEYID --registry-id ID` with `--min-snapshot N`, the latest snapshot sequence the owner knows (required: a writer can serve an older operator-signed snapshot that binds `none` or an earlier chain, and the owner's statement, not the file served, says which is latest; review of 208294e). It warns that it refuses `NAME/rotations` as served when they do not extend it. Two different chains that both extend it and reach the owner (possible only before a snapshot binds the latest hand-over) are refused, never chosen between; the operator's next snapshot binds one. The snapshot must record the rotating key as the package's owner: an older one recording an earlier owner binds a shorter chain, which a stolen earlier owner key can extend to the current owner its own way, so a stale `--min-snapshot` built on the thief's chain again (adversarial review of 65cab4f). While the owner stays the same, the operator keeps the chain it bound, so any snapshot recording the current owner binds the chain the operator admits from. A package the snapshot does not list, or lists under another owner, rotates after the operator's next snapshot. Where the snapshot binds no rotations, the owner has held the package from its first index, and nothing served or kept is built on: a writer's junk file there blocks nothing (same review). If the registry keeps no rotations that extend the bound ones, the rotation is refused until the operator's next snapshot restores its copy. `--no-snapshot` is explicit, for a registry without an operator: every chain reaching the owner must then be the same one. A recovery key remains the better choice: a stolen owner key cannot sign rotations at all.
- **This machine's record of the snapshots it verified.** `--min-snapshot` is the owner's statement, and a stale one let a writer serve an older snapshot that still records this key as owner, binding a shorter chain (review of 9f1b37c). So `rotate --operator` also keeps, per registry ID and operator key, the highest snapshot sequence of that key's this machine has verified and the operator chain it saw, recorded under every key of that chain, the keys handed away from included (`$XDG_STATE_HOME/coven/snapshots/`, beside `coven/signed`; written whole and renamed into place, opened without following links). A snapshot older than its signer's record is refused, whatever `--min-snapshot` says, and the record only rises. Only the signer's: a retired key, stolen, can sign any sequence, which never binds its successor's snapshots. A machine without a record (a new one) falls back to `--min-snapshot`, and a record kept under another operator key does not apply. `fetch --operator` (a snapshot given with `--snapshot` too) makes the same checks (`fresh_snapshot`) and records its signer's floor once it is decided, after its engine run has verified every signature (review of 88c38ae: it took only the floor, and recorded nothing). It does not record the operator chain: a client's chain is its trust store's (Grimoire's), which can forget one that a stolen retired key forked (`--forget-operator`); a chain recorded here could not be forgotten that way.
- **The window after a hand-over, without a recovery key.** A new owner rotates again only once the operator's next snapshot records it as the owner: until then its rotation is refused. A thief holding the new owner's key is not held back in that window, since it can rotate with `--no-snapshot` or with other tools, and only the operator's next snapshot decides which chain it admits. Nothing Coven checks on the owner's machine can close this without a recovery key, which is the way out: with one, owner keys sign no rotations at all (`publish --recovery-key`, at the package's first signed publish). The refusal says so.
- **Pin the current operator key.** `rotate --operator` should name the registry's current operator key. Pinned to a key the role was handed away from, a writer can serve `operator-rotations` cut short (or none), and that retired key, if stolen, signs a snapshot the rotation would trust. A machine whose `rotate` has seen the hand-over, pinned to any key of the chain, refuses (in `rotate` and `fetch`) a pinned key it saw handed on, and refuses operator rotations that do not extend the chain it saw. A machine that never saw the hand-over cannot tell, so pinning the current key is the owner's part.
- **Withdrawing after a rotation.** The current owner withdraws any version the index lists, including versions signed by an earlier key or published by a thief (review).
- **The chain.** The statements must form one chain from the first owner to the index's signer, and never return to an earlier key. A version is admitted when the index lists it and its release is signed by any key in the chain, so versions published before a rotation stay valid.
- **What fetch reports.** For a package with an index, `fetch` prints `owner K`, `owners K...` (the verified chain), `recovery R` and `index S` as soon as the index is verified, before any refusal for a withdrawal. A client therefore keeps the floor it has seen even for a version it is refused.
- **Pins.** `fetch --expect-signer K` admits a package that K owns or that was handed on from K. `--expect-recovery R` requires the index's recovery key. Grimoire pins both in its lock and records the new owner when it locks again. After that, a registry that drops the rotation is refused.
- **The old key.** A key the package was handed away from cannot publish, refresh or withdraw any more.
- **Limits.** The first signed release decides the owner and the recovery key (trust on first use). A recovery rotation signs over the entries of the index it starts from. If the registry put back an older index and `--min-sequence` lags behind, a withdrawal can be lost, and the new owner must withdraw the version again. A client pinned to an old key that has not yet seen a rotation can be shown a stolen old key's index by a registry writer who removes the rotation, until it locks again. TUF has the same gap for a client that has not fetched the next root. Through the registry snapshot, a writer without the operator key cannot do this: the operator does not admit an index whose signer no rotation reaches. An index signed for another registry, by the same key and for the same package name, can be served in this one, because indexes do not name their registry; use a different key per registry. The owner's copy is per machine, so a new machine trusts the registry's index on first use.

**The registry snapshot.** The registry has an operator, separate from its publishers: whoever runs it ("we'll run the registry ourselves", 2026-11-20). The operator's key signs `REGISTRY/snapshot`, which says which index of every package is current (TUF's snapshot and timestamp roles, in one). Publishers never hold this key, and the operator holds no publisher's key.
- **What it lists.** A witchy-2 object of role `snapshot`: `witchy/v2/snapshot\0coven-snapshot 4`, `suite witchy-2`, `operator witchy-2 <base64>` (its signer's public key), `registry ID` (the registry's identifier, set by its first snapshot with `--id` and never changed: a snapshot or rotation that the same key signed for another registry is refused), a sequence number that grows with each snapshot, and an expiry time (24 hours by default, `--valid-hours` up to 744). Then one line per package: `index NAME SEQUENCE sha384:DIGEST OWNER RECOVERY CHAIN` (key IDs; a sequence of at most 2^53-1, see Bounds), with the SHA-384 of that index's exact bytes and CHAIN the `sha384:` digest of the rotations bound, or `none`, or `unsigned NAME` for a package without an index. Then one line per hand-off the operator has seen, `handed NAME KEY` (the key that handed the package on). Then `signature <base64>`, the operator key's ML-DSA-65 signature of everything before it.
- **Who signs it, and when.** `coven snapshot --registry R --key OPERATOR` is a separate step, run by the operator: on a schedule shorter than the expiry, and after publishes it should make visible. `publish`, `yank`, `revoke`, `rotate` and `refresh` stay the publishers' and never need the operator key. A publisher's change reaches clients with the next snapshot. Until then, a new version is not published to clients (the index the snapshot names does not list it), and a new package is not either (`not in the registry's snapshot`). Why a separate step and not a hook in publish: a publish would then need the operator key, or an online service holding it. The operator keeps it offline, and the delay is bounded by how often it runs.
- **Consistent snapshots.** For each index it lists, the operator keeps the exact bytes as `NAME/indexes/SEQUENCE`. A client reads the index the snapshot names from there, never `NAME/index`, which publishers keep updating. A publish that is not in a snapshot yet therefore leaves every earlier version fetchable.
- **Bound rotations.** Each entry also binds the rotations its owner was reached through: the SHA-384 of their exact bytes, kept as `NAME/chains/HEX`, or `none`. A client follows the owner chain from that copy, never from `NAME/rotations`. Before this, the rotations were read live: while a recovery rotation was present and not yet admitted, nobody could fetch the package, and a writer who deleted it got the thief's index served again under the client's original pins. A writer now cannot choose whether a chain is served. A new entry is admitted only if the rotations served reach its index's signer. While the owner stays the same, the entry keeps the chain it bound.
- **What the operator admits.** The operator decides from its own copy of the last snapshot it signed (`$XDG_STATE_HOME/coven/operator`), never from the registry's, which a writer can put back. A package's entry changes only to an index that:
  - is newer (a higher sequence), by at most 2^20;
  - keeps the recovery key;
  - is signed by the previous owner, or by a key the rotations hand the package on to from the previous owner. The rotations are verified under the recovery key the previous entry recorded. A chain cut short, ending at a key handed away from, is refused (adversarial review of c00d6a6). If a recovery rotation hands on from an earlier owner than the recorded one, the entry stays, and the operator must resolve it by hand.
  - if it is signed by the previous owner, is not from an owner that the rotations served now hand on. A thief with the old key, racing a recovery rotation by putting back an index of its own, does not keep the package. The new owner's next update (`refresh`) is admitted.
  - comes with rotations that read as one chain under the recorded recovery key and extend, statement by statement, the ones the entry bound. Rotations that cannot be read, or that were deleted, truncated or rewritten, keep the previous entry (fail closed; review of 9710ad0).
  - is not signed by a key the operator has seen hand the package on. The operator records every hand-off it sees, admitted or not, in the snapshots it signs (`handed NAME KEY` lines), so the record travels with the operator-signed snapshot: a new operator machine, which builds on that snapshot, has it, and so does a new operator key after `rotate-operator`. A writer cannot drop a line without the operator key (review of 9cb1718: a per-machine file was read as empty on a new machine). A writer can put back an older snapshot of the operator's own, from before a hand-off was recorded, so a machine whose base would be the registry's snapshot, and not its own copy, refuses unless the operator states the highest sequence it knows it signed (`snapshot --min-base N`, `rotate-operator --min-base N`, 1 or above; from the operator's own records, never the sequence the registry serves), and then refuses a served snapshot older than that (adversarial review of 384ab92). `--min-base` applies to whichever base is chosen, the machine's own copy included: an old operator machine's copy is stale too, and a writer can put back exactly that snapshot, so that the machine would sign a sequence already signed, without the hand-offs recorded since (adversarial review of 363f952). Nothing on the machine tells a stale copy put back from the latest, so `--min-base` is required for every snapshot after the registry's first, and for `rotate-operator`: the operator's statement is the authority, never the machine's copy or the registry's file (review of e4cab48: run without it, a stale machine still signed a sequence again and admitted the stolen key). The registry's first snapshot is likewise stated (`snapshot --first --id ID`), never inferred: no snapshot served and no copy on the machine is also what a writer who deleted the snapshot shows a new operator machine, which would sign snapshot 1 again without the hand-offs (review of 2a41f8b).
  - comes with rotations that extend the bound ones, or else is read against the bound ones: if the rotations served were deleted, truncated or rewritten, the operator takes the bound rotations' own bytes (from `NAME/chains/HEX`, or its own copy under `$XDG_STATE_HOME/coven/operator/chains/`), with the statements served appended after any overlap with the bound chain's end (`[bob→carol, carol→dave]` over a bound `[…, bob→carol]` adds `carol→dave`; adversarial review of 363f952), or alone. So deleting `rotations` and `chains/` freezes nothing: the owner's updates are still admitted, and the operator restores the registry's copy from its own (adversarial review of 9cb1718). Without either copy (a new operator machine, both deleted), the entry stays. A thief who races a recovery rotation and then deletes it therefore does not get the old key's index admitted.

  Otherwise the previous entry stays, with a warning. A writer who rolls a package back, or plants an index under its own key, therefore holds back only that package, and the owner's next update is admitted. A package the registry no longer serves keeps its entry.
- **The operator's base.** The operator builds each snapshot on its own copy of the last one it signed. It uses the registry's snapshot only when that was signed by its own key on another machine and is newer. A snapshot of its own key that the registry serves older than its copy, or different at the same sequence, and a served snapshot that does not parse or names another registry, are refused, never signed over: the operator restores its latest snapshot to the registry (adversarial review of 363f952). It never builds on a snapshot signed by a predecessor key: that key was handed away from, may be stolen, and can sign one at any sequence (reviews of c00d6a6). `rotate-operator` signs the new key's first snapshot, so a new machine finds that one in the registry, or the operator restores it. Every later snapshot is above the hand-over's sequence. The registry's identifier also comes from the operator's own copy, or else from `--id`. It is never taken from the registry's files, where a snapshot the same key signed for another registry could be replayed. The operator writes each `NAME/indexes/SEQ` through directory descriptors opened from the registry root without following links, under a random staged name. Coven reads back each snapshot before writing it.
- **What `fetch` checks.** `fetch --operator KEYID --registry-id ID` verifies the registry's snapshot, or with `--snapshot FILE`, a copy the client kept. The snapshot must be signed by the operator reached from KEYID (`witchy-2:<hex>`), no older than `--min-snapshot`, and not expired. The package's index must be the copy whose digest the snapshot lists. A fetch prints `snapshot N` first. `coven verify-snapshot --registry R [--operator KEYID --registry-id ID] [--min-sequence N] [--keep FILE]` verifies the snapshot once, prints `snapshot`, `registry`, `operators` and `expires`, and keeps its bytes for the fetches of one resolve. Grimoire uses it this way. A fetch with neither `--operator` nor `--no-snapshot` is refused: skipping the snapshot is explicit.
- **What a registry writer without the operator key cannot do:**
  - **Mix and match.** It cannot serve indexes from different moments together: each must have the digest the one verified snapshot lists.
  - **Freeze.** It cannot keep the whole registry at an old state past the snapshot's expiry.
  - **Hide.** It cannot show an older snapshot to a client that has seen a newer one (`--min-snapshot`; Grimoire keeps the floor). That covers a newer index of a package the client has never fetched.
- **Operator rotation.** `coven rotate-operator --registry R --key OLD --new-key NEW` appends to `REGISTRY/operator-rotations` a statement, a witchy-2 object of role `operator-rotation` (`coven-operator-rotation 3`, signed in the engine by the old key's `Signer` granted `sign/witchy-2/operator-rotation`, never the snapshot's role), that hands the role of this registry (`registry ID`) from the old key (`from`, its whole public key, which verifies the statement) to the new key by its key ID (`to witchy-2:<hex>`, the digest of the key its snapshots must carry), from sequence N on. N is the sequence of the new key's first snapshot, so every snapshot the old key signed is below it. The new key then signs that snapshot. Both are signed before either is written, so a new key that fails to sign leaves no hand-over. A client pinned to an older key follows the chain. Coven checks the chain from the key it is given, and also against the chain an owner's `rotate` recorded on this machine (above): a machine that saw the role handed on refuses a pin of the old key and asks for the current one. Otherwise the client keeps the chain, as below. The client keeps the longest chain it has verified and refuses one that does not extend it, which Grimoire's trust store does. A registry serving a shorter chain, or none, therefore cannot roll a client back to an old key. The statements must form one chain, each signed by the key it hands the role from. A key the role was handed away from signs no snapshot and no rotation.
- **No recovery key for the operator, by decision.** A package's recovery key exists because a stolen owner key can sign releases that consumers run. A stolen operator key cannot. Every index is still signed by its package's owner and checked against the owner pins, so the operator key only chooses among indexes their owners signed: a freeze or a mix, bounded by the snapshot's expiry and the client's floors. Recovering from its theft is a new operator key, announced outside the registry: projects update `[registry] operator`, and machines run `grimoire trust --forget-operator`. A second root key would add a key to guard, for a role whose compromise is already bounded.
- **No separate timestamp role, by decision.** TUF splits the timestamp from the snapshot so that a large snapshot can be signed rarely while a small timestamp is re-signed often, by a key kept online. Here the snapshot is one line per package and is signed by the same operator who would sign a timestamp. Its own short expiry gives the freshness bound.
- **Limits.**
  - An unsigned package's snapshot entry says only that it exists. Its versions are not listed (no index), so the lock's digests are what protect it.
  - A client that pins an old operator key and has never seen its rotation accepts that old key's snapshot if a writer removes the rotation. This is the same gap as for package owners and TUF roots. A machine that saw the rotation refuses it.
  - An operator on a new machine, with no copy and with the registry's snapshot deleted, starts again at sequence 1. Clients that saw more refuse it, which fails closed. Keep the operator's state directory.
  - A rotation reaches clients with the next snapshot. Until then, clients are served the previous owner's index and chain, which the snapshot binds. After a recovery from a stolen key, that may still be the thief's index, so snapshot right after a rotation.
  - A planted `.snapshot.lock` blocks snapshots (denial of service).
  - `snapshot` and `operator-rotations` are the registry's own files, so they are not package names.

**Not built, and why.**
- **CI build identity** (OIDC-bound publishing, build attestations). Releases here are published from source by a key holder, and consumers compile the source themselves. There is no binary artifact whose builder identity would need proving. This becomes relevant when a registry accepts publishes from CI or distributes builds. The research report's "first public registry" phase lists the checks it would need.

## Package tests

Run `grimoire test .` here to check release framing, the private length decoder, fixed limit and two directory role readers with Witchy fixtures. `grimoire test . --list` shows the test and external provider signatures. Supply one tree with `grimoire test . --read-root roles=/absolute/tree` to use real role files. The suite lends `publisher/` and `reviewer/` separately. Their `role` files contain one byte, 1 and 5 respectively. An explicitly offered root with the wrong right or unavailable children blocks the role case. The two directories can also be pinned individually with `--read-dir 'test.wy::roles:left=/absolute/publisher'` and the corresponding `right` grant.

The independent client uses the same checked case. Run `./decoder_trials.py --guided --save corpus.json` for a bounded guest-coverage campaign or `./decoder_trials.py --replay tests/regressions/length.json` for the checked-in public regression corpus. Its reference decoder reads the first four bytes as an unsigned big-endian word and returns 4294967295 on short input.

## Package releases

Coven reads publication manifests as TOML 1.0 in a Witchy worker. The
launcher builds this worker with the configured `witchyc` and runs it
with the Wasmtime host. The worker can read the selected manifest, with
a 128 KiB limit. Coven checks the returned package coordinate and resolves
the requested source and its imports within the package directory.
Grimoire supplies `--manifest-pin` to `coven pack` and `coven publish`.
Coven checks the SHA-384 of the exact bytes parsed by the worker. Pass
the absolute, resolved manifest path when using this option directly.

Use `coven inspect RELEASE.coven` on the output of `coven pack PACKAGE` or a Grimoire library build. It prints the package name and version, exact dependencies and the SHA-384 content digest. For a release of several files it also prints the entry and each file's path, length and SHA-384, after checking each against the bytes. Publisher identity and admission are established separately by signed fetch.
