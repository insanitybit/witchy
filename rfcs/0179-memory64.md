# RFC-0179: 64-bit linear memory

A witchy program runs in one 32-bit Wasm linear memory, so its whole heap is
capped at 4 GiB. Programs that hold large data sets need more. Wasm's memory64
extension gives a 64-bit address space. This RFC makes 64-bit memory the one
production mode, and plans how to win back the per-access cost it brings.

## Decision

- **One mode: 64-bit.** Supporting both widths in production doubles the
  ABI, admission and test surface for a choice most users should never have
  to make. Every admitted program uses a 64-bit memory.
- **Parameterized on `PointerWidth`.** The change touches every place that
  bakes in 32 bits today, so it is made once as a parameter rather than a
  second rewrite of constants. `PointerWidth::W32` stays available to tests
  and to measurement, so the cost of the width itself can always be
  re-measured. It is not a supported user mode.

## What changes

`PointerWidth` is fixed before lowering and reaches every stage:

- **Layout.** Pointer fields and pointer slots in records, lists and
  dictionary tables are sized by the width (`layout/specialized.rs`, 4 bytes
  today), so record layouts and packed element strides grow.
- **Extents.** The counted header stores `count` and `capacity`, and lowering
  guards allocations against `u32::MAX - header` (about 120 such limits
  across lowering, the checker, the encoder and the runtime). Each limit is
  restated from the width.
- **The encoder.** `Ref` and `Size` map to the width's integer type
  (`canonical_wasmir/emit.rs`), and the inlined allocator, release and
  collection kernels (about 150 fixed 32-bit loads and stores) take their
  types from it. `memory.grow` and the memory type follow.
- **The host ABI.** Every import that passes `(ptr, len)` takes the width's
  integers, and the runtime reads guest memory through 64-bit offsets with a
  range check per call.
- **Admission.** The independent planner (`canonical_wasmir/plan_match.rs`)
  re-derives every function body, local type and memory instruction from the
  same width, token for token.
- **The checker.** SafeWIR's extent and allocation-size rules are stated
  against the width's maxima.

## Cost (measured)

A 32-bit memory lets Wasmtime reserve its whole 4 GiB range plus guard pages,
so a load or store needs no bounds check (`bounds_checks.rs` in
`wasmtime-internal-cranelift` 49: the elision case asserts a 32-bit index). A
64-bit memory cannot be covered that way. Its best case in Wasmtime 49 is a
memory that never moves, with a fixed reservation: each access compares its
index plus its own offset against a constant and, with Spectre mitigation on,
selects a trapping address instead of branching.

That path can be forced on today's 32-bit modules by removing guard pages and
fixing the reservation below 4 GiB. Doing so isolates the per-access check
cost from the pointer-width change. Measured 2026-10-08, release build,
minimum of 3 runs, twice:

| Benchmark | wasm32 (ms) | 64-bit bounds path | without Spectre select |
|---|---|---|---|
| reverse-complement | 21.2 | 36.9 (+74%) | 32.1 (+51%) |
| knucleotide | 17.9-20.6 | 28.9-29.8 (+45-65%) | 23.0-27.6 |
| dict_count | 25.4-30.9 | 39.9-40.3 (+30-57%) | 34.4-35.8 |
| word_count | 48.0-49.4 | 66.4-67.0 (+37%) | 59.4-62.2 |
| binary_trees | 149.7 | 203.5 (+36%) | 170-174 (+15%) |
| list_index | 3.3 | 4.3 (+30%) | 3.7 |
| nsieve, fannkuch | 5.0, 183 | 5.6, 205 (+12%) | 5.5, 197 |
| fasta, mandelbrot | 305, 36.8 | 323, 36.8 (+6%, 0) | ~305, 37 |

Wider pointers come on top: pointer-heavy layouts grow, and so does cache
traffic. The Spectre select stops a guest from speculatively reading outside
its memory. It is not traded for speed.

SafeWIR already proves most accesses in bounds, but Wasm cannot carry that
proof to the engine, so the engine checks every access regardless.

## Recovering the cost

Three engine-side strategies were measured on the same 32-bit modules, plus
one compiler-side change. Native instruction counts are deterministic.
Timings were taken on a loaded host (load average 14-17), paired run by run,
minimum of 9-11, and are indicative only.

| Strategy | Added native instructions over wasm32 (reverse-complement / dict_count / binary_trees / list_index) | Time over wasm32 |
|---|---|---|
| Wasmtime 49 64-bit path (above) | +44% / +47% / +45% / +44% | +34% to +118% |
| **Guarded index** (engine patch, below) | +29% / +31% / +28% / +28% | +8% to +43% |
| Address masking (engine patch, below) | +8% / +8% / +9% / +8% | +1% to +18% |
| Constant offsets folded into `memarg` | no change | no change |

- **Guarded index.** When the guard region is at least `offset + size`, check
  `index > reservation` once and guard the *index* (an out-of-range index
  becomes `reservation`, which lands in the guard region and traps), then add
  the offset. Every access is still checked and every out-of-range access
  still traps, exactly as the Wasm specification requires. Unlike Wasmtime
  49's precise per-offset compare, the check no longer depends on the
  offset, so accesses through one index share it. It is a ~25-line change in
  `bounds_checks.rs`. It removes about a third of the added instructions. Little more is shared, because most
  accesses go through a fresh index.
- **Address masking.** Reserve a power-of-two range plus a guard region and
  compute `index & mask`, with no compare and no select. It is cheapest, and
  it keeps the guest inside its sandbox. But an out-of-range index wraps to a
  different in-range address instead of trapping. That breaks the Wasm
  semantics, and it breaks witchy's rule that disagreement is a loud error,
  never a different answer: a checker bug would read the wrong object
  silently. **Not chosen.**
- **Folding constant offsets.** About 90% of our loads and stores carry
  `offset=0` and add a field offset with `i32.add` first. Folding those adds
  into `memarg` changes no native instruction, because Cranelift already
  folds them into the addressing mode. Not needed.

The engine can win back only about a third this way, because most accesses
go through a fresh index. Full recovery needs the engine to *know* an
index's range, the way it does today for a 32-bit index.

## Prior art (surveyed 2026-10-08)

- **Engines agree on the cost.** SpiderMonkey reports memory64 at 10% to
  over 100% slower than wasm32 and calls full recovery "impossible" for
  general modules [1]. Wasmtime measured explicit checks at 1.2-1.8x, and
  SpiderMonkey shows the same 1.52-1.56x with guard pages turned off, so
  neither engine has a trick the other lacks [2][3]. Our measurement
  (+6-74%) fits. "Impossible" holds for arbitrary Wasm, where the engine
  must assume any index. Our case differs: the compiler that shapes every
  module is ours, so we can emit index shapes the engine can bound (R2, R4).
- **Wasmtime's own roadmap matches R1.** Wasmtime already uses
  `index > bound`, with the offset absorbed by a guard, for dynamic memories
  with a guard region, which lets comparisons be shared [3]. The open issue
  #6094 also proposes removing a `select_spectre_guard` when a dominating
  access already trapped on the same condition, plus a narrow
  constraint-elimination pass. Its estimate is 1.08-1.15x. R1 extends the
  `index > bound` form to the fixed-reservation case 64-bit memories use,
  and adopts the dominating-guard elimination. Both fit work Wasmtime
  already plans.
- **Two-level guard pages** (Döllerer and Engelke, VMIL 2024 [4]). There is
  no compare and no branch. Each access first performs one extra probe load
  from a "macro guard" table: one host page per GiB of address space,
  mapped read-only where memory exists and unmapped elsewhere. An
  out-of-range access faults on the probe, so traps stay exact. Measured in
  Umbra on SPEC CPU2017 and k-means: 12.7% mean and 17.3% worst, against
  76-142% for compare-based checks. Not chosen as the primary path: the
  real access does not depend on the probe, so it can execute speculatively
  out of range. That is a Spectre gap our Spectre-guarded design does not
  have. Worth measuring as R3's fallback for accesses that loop hoisting
  cannot reach, if it can be made data-dependent (for example, by adding
  the probe's loaded zero into the address).
- **Hardware.** Cage (CGO 2025 [5]) replaces memory64 software checks with
  Arm MTE: up to 34% faster than plain wasm64 on Pixel 8. Apple's A19/M5
  ship Enhanced MTE (Memory Integrity Enforcement) [6], and V8 lists CHERI
  as a way to make memory64 cheaper. These are host-specific, so they are
  later adapters behind the same engine contract, not the plan.
- **Masking is common in research.** Cage masks the index before computing
  the address [5]. That confines a stray access but turns it into a
  different in-range access. Our rejection of masking stands.
- **Hazard: R4's address shape.** CVE-2026-34971 was an aarch64 Cranelift
  miscompile of `load(iadd(base, ishl(index, k)))` on 64-bit memories with
  Spectre mitigation or signal-based traps off. It let a check pass and a
  different address load: a sandbox escape. Fixed in Wasmtime 36.0.7,
  42.0.2 and 43.0.1; we run 49. R4 emits exactly this shape, so it keeps
  Spectre mitigation on and adds a differential fuzz target for shifted
  reference loads on aarch64 and x86-64.

[1] https://spidermonkey.dev/blog/2025/01/15/is-memory64-actually-worth-using.html
[2] https://docs.wasmtime.dev/examples-fast-execution.html
[3] https://github.com/bytecodealliance/wasmtime/issues/6094
[4] https://dl.acm.org/doi/10.1145/3689490.3690400
[5] https://arxiv.org/abs/2408.11456
[6] https://support.apple.com/guide/security/sec8b776536b

## Recovery plan: all of it back

**Target.** Each benchmark under 64-bit memory runs at least as fast as the
frozen wasm32 baseline (master at 698c3bf13, the table above). Separately,
with the same compiler, 64-bit costs at most 2% over `W32`. The first target
can be met by compiler wins that would also speed up wasm32. The second
target cannot, which keeps the engine work honest. Evidence comes from
paired runs on a quiet host plus native instruction counts.

**Principle.** The engine stays the sandbox wall. Every check removed is
proven by the engine from the code it compiles, never taken on trust from
SafeWIR. Trusting the checker would turn a checker bug from a wrong answer
into a sandbox escape. It is the one shortcut this plan rules out.

The losses come from three sources, and each gets its own remedy:

| Loss | Remedy | Where |
|---|---|---|
| A check on every access | R1 guarded index, R2 range-based elision, R3 loop hoisting | Wasmtime / Cranelift, patched in-tree (`vendor/wasmtime-internal-cranelift`) |
| Wider pointers (layouts, cache) | R4 compressed references | witchy layout and encoder |
| Accesses themselves | R5 fewer loads and stores | witchy compiler |

- **R1. Guarded index** (above). One check per index, with the offset
  absorbed by the guard region. Measured at about a third of the added
  instructions. Adds Wasmtime #6094's dominating-guard elimination: a
  `select_spectre_guard` whose condition an earlier, dominating access
  already trapped on is dropped.
- **R2. Range-based elision.** Wasmtime elides a 32-bit index's check
  because its type bounds it below 4 GiB. Generalize that rule from the
  index *type* to the index *value*. If Cranelift can bound the index, for
  example `uextend` of an `i32`, a shift of one, a masked value, or a
  constant, and the bound plus `offset + size` stays within reservation plus
  guard, emit no check. Today's wasm32 elision is the special case. This is
  sound for any module, not only ours.
- **R3. Loop range-check hoisting.** For an access indexed by an induction
  variable that runs `start..end` by a known step, check the largest index
  once before the loop, not on every iteration. This covers the byte and
  element scans behind the worst cases: reverse-complement, knucleotide,
  `list_index`, nsieve.
- **R4. Compressed references.** Store an object reference as a 32-bit
  value scaled by the allocation alignment: `address = ref << 3`, which
  reaches 32 GiB. Pointer fields stay 4 bytes, so layouts and cache traffic
  match wasm32. Under R2, every access through a reference has a known range
  (`uextend(i32) << 3`, below 32 GiB), so it needs no check with a 32 GiB
  plus guard reservation. Only byte and element offsets inside a large
  buffer carry 64-bit indices, and R3 covers those in loops. `PointerWidth`
  becomes the stored reference encoding: compressed with a shift (3 for
  32 GiB, 4 for 64 GiB), or full 64-bit for heaps beyond that. The encoding
  is chosen from the heap grant at compile time.
- **R5. Fewer accesses.** This is the existing optimization queue, counted
  as recovery: scalar replacement and loop-invariant header and length
  loads, reference-count traffic (RFC-0178 regions, Perceus-style
  borrowing), and denser layouts. It speeds up every width and closes
  whatever R1-R4 leave.

**Order and gates** (each step lands only with its measurement):

1. `PointerWidth` parameterized, defaulting to today's output, byte-identical.
2. Full 64-bit references working end to end. Measure the true cost (check
   plus width).
3. R1 and R2 in the vendored Wasmtime crate. Engine patches are carried
   in-tree, never sent upstream. Measure.
4. R4 compressed references as the default encoding. Measure. Expected:
   object-graph code at wasm32 cost.
5. R3 loop hoisting. Measure scan-heavy benchmarks. For accesses that
   neither R2 nor R3 covers, measure a data-dependent two-level guard probe
   against R1's compare.
6. Switch the default to 64-bit memory once the 2% target holds, or holds
   on everything except benchmarks named in the ledger with the remaining
   gap and the R5 item that closes it.
7. R5 continues. The absolute target closes when every benchmark is at or
   under its frozen wasm32 baseline.

## Probe: range-based elision on a real 64-bit memory (2026-10-08)

Today's admitted modules were rewritten into true memory64 modules: every
address became `i64.extend_i32_u` of the old 32-bit address, with the memory
declared 64-bit and a fixed 8 GiB reservation. That is R4's address shape
without its shift. R2 was prototyped as a ~70-line change to Wasmtime 49's
`bounds_checks.rs`: an upper bound on the index derived from `uextend`,
`iconst`, `iadd`, `ishl` by a constant and `band` with a constant. The
check is dropped when bound + offset + size fits within reservation plus
guard.

Native instructions, whole module (spectre selects in parentheses):

| Benchmark | wasm32 | memory64, Wasmtime 49 | memory64 + R1 | memory64 + R2 |
|---|---|---|---|---|
| reverse-complement | 6943 (0) | 9909 (557) | 8967 (557) | 6971 (0) |
| dict_count | 4212 (0) | 6040 (348) | 5522 (345) | 4264 (0) |
| binary_trees | 4091 (0) | 5839 (331) | 5284 (321) | 4113 (0) |
| list_index | 2930 (0) | 4162 (244) | 3806 (244) | 2946 (0) |
| knucleotide | 8580 (0) | 12385 (706) | 11126 (695) | 8633 (0) |

Time: paired runs, minimum of 11, host load 10-14. The variants use
distinct engine configurations so that Wasmtime's compilation cache cannot
serve one variant's code to another.

| Benchmark | memory64 | + R1 | + R2 |
|---|---|---|---|
| reverse-complement | +83% | +40% | -2% |
| knucleotide | +40% | +35% | +11% |
| dict_count | +61% | +46% | +2% |
| word_count | +23% | +20% | +1% |
| binary_trees | +41% | +24% | -2% |
| list_index | +39% | +15% | -12% |
| nsieve, fannkuch | +7%, +16% | +1%, +13% | -6%, 0% |
| fasta, mandelbrot | +13%, -1% | +3%, -1% | +1%, -2% |

**A real 64-bit memory whose addresses the engine can bound runs at wasm32
speed.** R2 removes every check, and what remains matches wasm32 within
noise. This confirms the plan's premise: with R4 (32-bit references scaled
by alignment) and 32-bit element counts, every address is a bounded sum.
The heap reaches tens of GiB at wasm32 cost. Only buffers indexed past 4 G
elements need 64-bit indices and fall back to R1 and R3.

R2's soundness is the wasm32 argument restated. The index is at most its
bound. The memory never moves. Everything from the base to reservation plus
guard is either accessible or unmapped. So an access either lands in bounds
or faults. A Spectre-speculated access stays inside the same reserved
range, exactly as it does for wasm32 today.

The probe was measurement-only code. R2 now lives in the tree as a patch to
the vendored `wasmtime-internal-cranelift` 49.0.2 (see Status).

## Status (2026-10-09)

**Landed.**

- **R2, range-based elision**, as a patch to `bounds_checks.rs` in the
  vendored `wasmtime-internal-cranelift` 49.0.2. The index bound walks
  `uextend`, `iconst`, `iadd`, `ishl` by a constant and `band` with a
  constant. The check is dropped only when the bound plus `offset + size`
  fits within reservation plus guard, the minimum memory is within the
  reservation, and the memory cannot move. Tests in
  `tests/misc/memory64_range_elision.rs` pin the boundary and show that
  out-of-range indices still trap.
- **A 64-bit memory as the one mode.** Every admitted module declares
  memory64 with a maximum of 65,536 pages. Addresses stay 32-bit values and
  are zero-extended at each access (`emit_memory_index`). The encoder,
  planner and kernels use the 64-bit forms of `memory.size`, `memory.grow`,
  `memory.copy` and `memory.fill`. The runtime enables memory64 with
  `memory_may_move(false)`, which R2 requires.
- **Allocator growth outlined.** The free-list search and the in-memory bump
  stay inline. Only memory growth calls the module's one `alloc` helper. A
  fully inline allocator pushed one generated async executor function past
  wasmparser's 7,654,321-byte function body limit.

**Departures from the plan.**

- **R1 was not needed.** R2 removes every check on our address shapes.
- **Step 1 was skipped.** `PointerWidth` is not a parameter, so `W32` is not
  available in the tree. The relative target was measured against the last
  wasm32 commit (95c7c6c60) instead. R4 is where the width becomes a
  parameter, as the stored reference encoding.
- **The heap is still capped at 4 GiB.** References are 32-bit byte
  addresses. R4 lifts the cap.

**Measured.** Same compiler, wasm32 commit 95c7c6c60 against master
d3104a467, release builds. Run-phase instructions retired are the count at
6x the benchmark's work minus the count at 1x, which cancels compilation;
the counts are deterministic. Cycles are the same difference, from a host
at load average 10 on 10 cores, interleaved, median of 5 to 9, so they
vary by several percent.

| Benchmark | Instructions | Cycles |
|---|---|---|
| expr_eval | -1.3% | +1.1% |
| knucleotide | -1.7% | +0.2% |
| fasta | +1.3% | +0.7% |

Every benchmark is within the 2% relative target by instruction count.
fasta's residual is register allocation in one large function: stack
reloads replace register moves. Wall-clock runs under the same load showed
+2% to +4% on these three; those gaps did not survive interleaving.

The admitted path does not run Binaryen, so Cranelift compiles the
encoder's bytes as emitted. Wasmtime 49's inliner charges every inlined
call against a per-caller budget (`inlining_sum_size_threshold`, 2000
dataflow values, which each zero-extension adds to). It also inlines the
cold growth helper at every allocation site, which can push small hot
helpers out of a large function. Keeping calls in cold blocks out of the
inliner fixed that, but it gave no measurable gain, so it was not landed.

## R4: compressed references for a large heap (amended 2026-10-09)

**Decision: two heap modes, chosen by the program.** As in HotSpot, where
compressed oops are a property of the heap size rather than a global switch,
the reference encoding follows the heap the program asks for:

| Mode | Declared by | Memory maximum | Reference | Address |
|---|---|---|---|---|
| Standard | default | 4 GiB | byte address | `uextend(ref) + offset` |
| Large | `@large_heap` on `main` | 32 GiB | eight-byte unit | `(uextend(ref) << 3) + uextend(offset)` |

The plan's step 4 made compressed references the default. It is not: a
standard program keeps byte references, byte-identical code, and no
rounding of allocation sizes. Only a program that needs more than 4 GiB
pays for the shift.

- **The marker is on `main`.** It is a property of the whole program,
  recorded in the launch contract (version 2 adds the heap byte) and the
  capability footprint (`heap   large (32 GiB)`). A newly declared large
  heap is a footprint widening in `caps-diff`. It works the same for a
  trusted executable and an untrusted one; only the grant differs.
- **The launcher grants the heap.** `witchy run`, trusted applications and
  tests grant it. `witchy sandbox` grants it only with `--large-heap`, so
  an operator decides. Build steps never get it. A refused growth names
  the limit and points at the marker.
- **The engine is separate.** A large program compiles for an engine with a
  48 GiB reservation, allocated on demand. A 64-bit memory gets no guard
  region, so the whole bound must fit the reservation: a shifted reference
  (below 32 GiB) plus four 32-bit addends. R2 bounds every address the
  encoder forms inside it, so
  every access is check-free as in the standard mode.
- **One encoding seam.** `RefEncoding {Byte, Scaled8}` in the encoder and
  the independent planner forms every address, size and allocator global.
  Under `Scaled8`, the allocator globals and free-list links hold units,
  sizes round to eight bytes, the RC header sits at `(ref << 3) - 8`, and
  static data is eight-aligned. Interior addresses that outlive one access
  are held in i64 locals. Admission still re-derives every body, so a
  divergence between encoder and planner is a loud plan mismatch.
- **Host buffers take 64-bit byte addresses** under `Scaled8`. Host
  functions are generic over the address width, and the linker picks the
  width from the admitted artifact's heap mode. Raw Wasm is standard.
- **A single value stays under 4 GiB.** RC sizes, collection counts and
  offsets inside one object stay 32-bit (the first open question below).
  The large heap is room for more values, not larger ones.

**Evidence.**

- `tests/misc/large_heap.rs`: objects placed past 4 GiB (heap above
  2^32 bytes, heap audit clean), large-heap argv, and a proptest op-script
  fuzzer that runs list, dictionary and string operations on both heaps
  against a Rust model.
- `tests/misc/memory64_range_elision.rs`: the R4 shape needs no explicit
  check on the 48 GiB reservation (36 GiB keeps checks on fields past the
  first offset), and a proptest fuzzes shifted loads at
  every width against a memory model, so an out-of-range load traps.
- All 124 example and benchmark programs, run with `@large_heap` added,
  print the same output as without it. The one exception,
  `rfc0153_std_show_dict`, exhausts the standard 1 GiB on master too; with
  the marker it no longer does.
- A standard program's Wasm is byte-identical to master's for all 194
  benchmark and example programs.

**Cost (measured 2026-10-09).** The same release binary, each benchmark
with and without `@large_heap`. Instructions retired in the run phase:
`main` wrapped to run the kernel six times and once, difference divided by
five, which cancels compilation.

| Benchmark | Standard (M) | Large (M) | Delta |
|---|---|---|---|
| binary_trees | 3239 | 3653 | +12.8% |
| expr_eval | 909 | 1050 | +15.5% |
| list_index | 103 | 111 | +7.8% |
| record_build | 22.6 | 24.3 | +7.3% |
| nsieve | 118 | 127 | +7.1% |
| knucleotide | 310 | 329 | +6.2% |
| dict_count | 873 | 919 | +5.3% |
| fannkuch | 3316 | 3400 | +2.5% |
| fasta | 4806 | 4908 | +2.1% |
| fib | 749 | 747 | -0.2% |
| mandelbrot | 422 | 419 | -0.7% |
| closure_calls | 92.2 | 89.9 | -2.5% |
| reverse-complement | 1400 | 1312 | -6.3% |

Getting here took three fixes, found by disassembling the generated code.
The first measurement was +33% to +39% on allocation-heavy kernels:

- Header words at `(ref << 3) - k` were an i64 subtraction, which R2
  cannot bound. They are now `(uextend(ref - 1) << 3) + (8 - k)`.
- `(ref << 3) + uextend(i32) + c` overran a 36 GiB reservation. A 64-bit
  memory has no guard region, so the reservation is now 48 GiB.
- An i64 address held in a local is a block parameter inside a loop, which
  R2 cannot bound. Copies keep the reference plus an i32 offset instead.

The vendored R2 path also moves a constant addend into the access's static
offset.

What remains is instruction selection. On aarch64 a 32-bit load cannot
scale a register by 8 in its address, so each access through a fresh
reference costs `mov`, `lsl` and a register-offset load, where `Byte` uses a
single `ldr [heap, w, uxtw]`. The remedy is T6: an ISLE rule lowering
`iadd(x, ishl(uextend(y), 3))` to one `add x, x, w, uxtw #3`. That needs
`cranelift-codegen` vendored with its extended-register ALU form taking a
shift. Until then a large heap costs up to about 16% on reference-chasing
code, and nothing on scalar code. Only programs that ask for it pay.

| Checker limits are stated per width | A forged module that exceeds the 64-bit allocation limit is refused |
| Host imports reject out-of-range 64-bit offsets | Every host range check uses checked arithmetic on the widened address; `wide_guest_ranges_reject_wrapping_sums`. One test per import family: open |
| Out-of-range accesses still trap | R2: `memory64_range_elision` tests (landed). R3: open |

## Open questions

- Whether `Size` should become 64-bit everywhere, or stay 32-bit for element
  counts while byte offsets widen. A 32-bit count halves header traffic, but
  it caps a single collection at 4 G elements.
- Whether a future Wasm proposal lets a module carry a compiler's bounds
  proof to the engine. None exists in Wasmtime 49.
- How RFC-0178 region chunks and the region-born address test size their
  ranges under 64-bit addresses. Expected: the same logic with wider words.
