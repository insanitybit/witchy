# RFC-0041: The witchy docs as a glamour app — a self-hosted, runnable book

> Provisional syntax/paths. Code blocks are intentionally **not** tagged `witchy`
> so the doc-examples test does not try to compile partial snippets.

## Summary

Build "The witchy Book" as a **witchy program** — a [glamour](0008-frontend-framework-rune.md)
app compiled to wasm, static-hosted, running entirely client-side — instead of as
static HTML generated by mdBook (a Rust tool). The app parses the existing
`book/src/SUMMARY.md` into its navigation, renders each page's Markdown through
`glamour`'s own `markdown.to_vnode`, routes between pages with a `UiRoute`, and turns
every `witchy` code block into an **editable, runnable cell** powered by the compiler
that already runs in the browser (`web/witchy.wasm` + `web/witchy-host.js`). There is
**no server**: the docs are static content served from static hosting; the compiler
runs in the reader's browser exactly as it does today.

This supersedes [RFC-0019](0019-interactive-documentation.md), which pursued the same
runnable-book goal by progressively enhancing mdBook's HTML output. It **keeps
RFC-0019's genuinely reusable core** — the client-side compiler engine (repaired and
de-duplicated) and the generated classification/validation manifest — and **replaces
its shell**: mdBook and its theme give way to a glamour app that witchy renders itself.

## Motivation

Two reasons, one strategic and one that removes a dependency.

**Dogfooding as the pitch.** witchy's whole story is "you can build real, safe
software with this." The most persuasive proof a language can offer is that its own
front door is built with it. Today the front door is generated by mdBook — a fine
tool, but a *Rust* tool; the docs demonstrate Rust, not witchy. We are unusually
well-positioned to change that, because every hard piece already exists and is proven:

- `markdown.to_vnode(md) -> VNode` renders Markdown to a glamour tree, XSS-safe by
  construction (every leaf is a `text` node; hrefs are scheme-checked). It is already
  used in production by `coven_web_app` to render fetched API docs to real elements.
- The browser compiler (`web/witchy.wasm`, the actual codegen path) already compiles
  and runs snippets client-side and is already validated against the interpreter
  oracle (`scripts/pg_validate.mjs`).
- glamour is now capability-safe ([RFC-0039](0039-glamour-capability-safe-effects.md)),
  routes client-side (`UiRoute`), and enters through a host-minted root cap on an
  exported step ([RFC-0040](0040-grantable-user-capabilities-on-exports.md)) — the
  exact shape `coven_web_app` ships.

So the docs can be a *sibling of coven-web*: a static, client-side glamour app. That
makes glamour, `std/markdown`, the browser target, and the language itself the
exemplars the project is trying to showcase — the docs stop being a thing *about*
witchy and become a thing *made of* witchy.

**No server, on purpose.** A natural question is "should the docs run their own witchy
server?" No. Docs are static content, and the runnable examples already execute fully
client-side. A server (whether serving pages or compiling submitted source) adds
hosting cost, latency, and — for a compile server — an **arbitrary-code-execution
trust boundary**, to deliver strictly *less* than the in-browser path we already have.
This RFC keeps the deployment a bag of static files (compiled app wasm + content +
compiler wasm) on static hosting. `std/server` is a great capability; the docs simply
do not need it.

## Design

The content and its authoring do not change: `book/src/*.md` stay plain Markdown, and
`SUMMARY.md` stays the navigation source. What changes is what turns them into a site.

Four phases. Phase 0 is the reusable RFC-0019 prerequisite (repair + share the browser
engine). Phases 1–2 build the glamour app and the runnable cells. Phase 3 is the
reusable RFC-0019 no-drift guarantee (manifest + CI + hosting).

### Phase 0 — One engine, repaired and shared (kept from RFC-0019)

Unchanged from RFC-0019 and still a hard prerequisite — the runnable cell needs a
working host shim regardless of the shell:

- Make `web/witchy-host.js` (`compile` / `runWitchy`, already oracle-validated) the
  single compile path. Delete the dead `witchy_run` call from `web/playground.js` (it
  references an export the oracle-only migration removed, so the standalone playground
  currently throws on first Run).
- Extract one highlighter (`web/witchy-highlight.js`) and one editor
  (`web/witchy-editor.js`) — a transparent `<textarea>` over a highlighted `<pre>`,
  Tab-inserts-spaces, ⌘/Ctrl-Enter to run — shared by the standalone playground and
  the docs app's cells. The hand-maintained keyword list lives in exactly one file.

### Phase 1 — The docs app shell (glamour)

A new witchy program under `projects/docs/` (sibling of `projects/glamour/examples/`),
built as a glamour app with the coven-web shape:

- **Navigation from `SUMMARY.md`.** A build step reads `book/src/SUMMARY.md` and emits
  a small JSON nav tree (title → slug, nesting) the app renders as the sidebar. This
  keeps `SUMMARY.md` the single source of navigation.
- **Pages via `markdown.to_vnode`.** The current route's Markdown is rendered to a
  glamour `VNode` by `std/markdown`. Content ships as static assets fetched by the host
  shell (a `UiFetch` scoped to the content directory) or bundled — see Phase 3.
- **Client-side routing.** Page links are `Cmd.Nav(UiRoute, slug)`; the host mirrors
  the path back as a route msg and the app re-renders — the coven-web routing pattern.
- **The MVU loop** is `export_step(ui: UiRoot, input) -> String` driven by
  `glamour-dom.mjs`; `main` is CLI convenience. The app's host footprint is empty; its
  authority is the narrowed UI tokens on the `user_caps` axis (RFC-0039).

At the end of Phase 1 the book renders and navigates as a glamour app — static parity
with today's book, minus interactivity.

### Phase 2 — Runnable cells

`markdown.to_vnode` tags each fenced block with its language — `<code class="language-witchy">`
(shipped: the code stays inert, escaped text, so no sink is introduced) — which is the hook
the host uses to find runnable blocks.

**A non-diffed host slot, rendered in the MAIN frame** (design settled during implementation
across two iterations — this section records the endpoint, not the false starts).

The *security* question and the *DOM-ownership* question have different answers, and conflating
them was the first mistake:

- **Security → the main frame, no iframe.** A reader's edited snippet compiles to a wasm
  module that is capability-DENIED by omission (the browser grants no `Dir`/`Net`/`Clock`/…
  imports), so it is already contained by wasm's memory isolation plus the capability model —
  it can only compute and return a string. It needs no sandboxed iframe; a `Compartment`'s
  `connect-src 'none'` would only get in the way (it would block loading the compiler wasm).
- **DOM ownership → a non-diffed subtree.** glamour OWNS and re-diffs the DOM on every message
  (a `GotNav` re-renders the page even though only the nav changed). A runnable cell that
  *mutates* glamour's DOM — wrapping the `<pre>` in a cell — is therefore clobbered on the next
  re-diff (verified: a no-op post-render hook renders fine; the mutating enhancer corrupts the
  page). So the cell must live in a subtree glamour does **not** diff into. glamour already has
  exactly this: `patch` returns a live `Compartment` node untouched. The runnable cell reuses
  that non-diff property (via the `Compartment` path or an analogous "host slot" VNode) — but
  the host mounts it in the MAIN frame as an editor + Run button, not a sandboxed iframe.

So the code block is emitted as a host slot glamour renders once and leaves alone; the host
builds the cell into it (the shared editor + a Run button wired to `witchy-host.js` /
`runWitchy` against the lazily-loaded `web/witchy.wasm`). Run stays host-managed (it never
dispatches a glamour msg). The cell-building + compile+run logic is already implemented and
tested standalone (`web/witchy-runnable.js` + `witchy-runnable.test.mjs`); wiring it is a
matter of the host-slot mechanism, not the cell itself. Compartments-as-iframes remain for
genuinely FOREIGN renderers (RFC-0015), where the isolation IS needed.

**Highlighting is host-side, so it stays XSS-safe.** The rune renders code as inert VNode
text (never an HTML sink); the host highlights the already-escaped `language-witchy` text
with the shared `web/witchy-highlight.js` (re-escaping as it tokenizes). Nothing in the rune
emits HTML.

Each block's behavior mirrors the existing `documentation_examples_are_valid`
classifier exactly, read from the Phase 3 manifest (never re-derived in JS):

- **console-only** → runs and prints in-browser (the set the test already runs on both
  backends).
- **needs `Dir`/`Net`/`Clock`/`Env`** → compiles, then errors when it touches the
  capability the browser's deny-by-omission shim never granted; the cell frames this as
  the capability model in action, not a bug.
- **expect-error teaching examples** (e.g. a `Dir[Read]` that calls `write`) → the cell
  presents the compile error as the expected, correct outcome.
- **actor / argv** → "Open in playground ↗" (deep-link via URL fragment) and a live
  editor if in-browser stable output isn't available.

**Capability badges + theme.** Each runnable cell renders its requested authority (the
footprint from the manifest — `Console`, `Dir[Read]`, …) as badges: "authority is a
visible, typed artifact" made literally visible. Theming is the app's own glamour view
+ CSS (the playground palette), so the book and playground look identical because they
*are* the same stack.

### Phase 3 — No silent drift + hosting (kept from RFC-0019)

- **Generated manifest.** Extend `documentation_examples_are_valid` (it already walks
  `book/src`, `spec`, root docs and classifies every block) to emit
  `book/examples.json`: per `(file, block-index)` `{ runnable, console_only,
  expect_error, capability_footprint, expected_output }`. A freshness test fails on
  drift (the `stdlib_docs_are_current` pattern). The browser reads what the Rust
  classifier produced — one source of truth.
- **Headless output check.** `pg_validate.mjs` loads the shipped compiler wasm and runs
  every `runnable` block, asserting output equals the oracle — the in-book run can never
  diverge from the toolchain.
- **CI + deploy.** The existing "Playground wasm build" job also builds the docs app
  wasm and drops it + `web/*.js` + content + `examples.json` into the deploy bundle
  (GitHub Pages). Per the house rule, every response carries strict
  `COOP: same-origin` / `COEP: require-corp` / `CORP: same-origin`. **mdBook is
  removed** (`book.toml`, `scripts/build-book.sh`'s `mdbook` path, the CI `mdbook` job)
  — break-don't-deprecate.

### What changes vs RFC-0019

| | RFC-0019 (superseded) | RFC-0041 |
|---|---|---|
| Shell | mdBook HTML + `additional-js` enhancement | glamour app (witchy → wasm) |
| Theme | custom mdBook theme | the app's own glamour view + CSS |
| Runnable cell | enhance `pre>code` in mdBook output | host-managed `Compartment` cell |
| Engine (Phase 0) | **same** — repaired, shared host shim/editor/highlighter | **same** |
| Manifest + CI (Phase 3) | **same** — `examples.json`, `pg_validate`, headless diff | **same** |
| Server | none (client-side) | none (client-side) |

## Alternatives

- **RFC-0019's mdBook + progressive enhancement.** Rejected as the destination: it
  demonstrates a Rust tool, not witchy, and cedes control of the shell. Its reusable
  parts (engine repair, manifest, validation) are carried forward here.
- **A witchy HTTP server for the docs** (`std/server`). Rejected: docs are static and
  the runnable examples run client-side, so a server adds hosting cost, latency, and
  (if it compiles submitted source) an arbitrary-code-execution boundary — to deliver
  less than the static + in-browser path. Static hosting wins on every axis.
- **A server that renders pages dynamically.** Same objection: nothing about static
  documentation needs a request/response server; it only adds an attack surface and an
  uptime dependency.
- **Docusaurus / Astro / a bespoke JS SPA.** Rejected: not witchy (defeats the
  dogfood), and a larger rewrite than a glamour app that reuses `markdown.to_vnode` and
  the coven-web pattern we already ship.
- **Per-block capability analysis in JS.** Rejected (as in RFC-0019): re-implements
  `capabilities::analyze` and could disagree with the authoritative Rust classifier;
  generate the manifest from the test instead.

## Drawbacks

- **We rebuild the reader shell mdBook gave free.** Navigation, folding, responsive
  layout, and especially **search** (mdBook ships elasticlunr). Nav/layout/theme are
  ordinary glamour view work; search is the real gap — Phase 3 can emit a small
  client-side full-text index (a JSON the app filters) as a bounded add, or search
  ships in a follow-up. This must be named, not hidden: losing built-in search is the
  main cost of leaving mdBook.
- **Two wasm modules on a page** (the docs app + the lazily-loaded 3.26 MB compiler).
  The compiler is fetched only on first Run and HTTP-cached across the whole book; the
  app wasm is small. Reading never blocks on the compiler.
- **More moving parts than "run mdBook"** — a build step (SUMMARY→nav JSON, content
  bundle, app wasm) plus the manifest. Phase 3 makes each CI-gated (freshness test,
  headless diff) rather than trusted.
- **Browser ≠ full toolchain.** The browser grants no `Dir`/`Net`/`Clock`/`Env`, so
  some examples compile but cannot fully run; framed as the capability model in action,
  but a real difference readers must not be misled about.

## Definition of done

- The docs are a glamour app (`projects/docs/`) compiled to wasm, static-hosted, no
  server; it renders every `book/src/*.md` page via `markdown.to_vnode` with
  `SUMMARY.md`-driven navigation and `UiRoute` client-side routing; its host footprint
  is empty.
- Every `witchy` code block is an editable cell; console-only blocks run in-browser and
  their output equals the interpreter oracle (enforced by the extended `pg_validate`).
- Each runnable cell shows its capability footprint as badges; expect-error and
  capability-denial blocks are framed as the correct outcome (from the manifest).
- The `examples.json` manifest has a freshness test; CI builds the app + compiler wasm,
  runs the headless output diff, and deploys with strict COOP/COEP/CORP.
- mdBook is removed; RFC-0019 is marked superseded-by this RFC.
- Phase 0 (engine repair) landed first so the standalone playground works again.

## Prior art

- `coven_web_app` (in-repo) — a static, client-side glamour app that already renders
  fetched Markdown docs to real elements: the pattern this generalizes to the whole
  book.
- [RFC-0019](0019-interactive-documentation.md) (the runnable-book goal + the engine
  and validation this reuses), [RFC-0007](0007-witchy-wasm-browser-target.md) (browser
  target + deny-by-omission shim), [RFC-0015](0015-secure-web-by-construction.md)
  (compartments; the safe Markdown renderer), `scripts/pg_validate.mjs` (the oracle
  diff Phase 3 extends).
- Compiler-to-wasm playgrounds (Roc, Gleam, Grain, Elm) and Pyodide/PyScript docs —
  "ship the real compiler as wasm, run client-side." This RFC goes one step further:
  the *docs site itself* is written in the language.
